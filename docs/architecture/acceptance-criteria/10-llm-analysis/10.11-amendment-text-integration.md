# Area 10.11 — Amendment Text Integration

> Project: `bill-analysis-pipeline` | Package additions
> **Driven by**: Component 7 §7.6 — `amendment.text.ingested` event and `amendment_text_chunks` table
> **Status**: Net-additions to existing `bill-analysis-pipeline`, not a new pipeline

## Purpose

Amendment text is now ingested as a first-class entity (Component 7 §7.5–§7.6). This area specifies how the LLM analysis layer consumes it: **multi-pass LLM analysis with complexity-based routing**, mirroring the bill side's tiered approach but applied directly to amendment text (no decomposition step). Output is `AmendmentFindingDO` rows tagged with `passNumber`. Component 11 §11.12 reads those findings when materializing stances on amendment-typed votes.

**Why amendment-level analysis, not just analyzed-as-part-of-bill:** the §7 design rationale stated this — amendments can substantively alter a bill's function (a substitute amendment can replace the entire bill body). Analyzing only the finalized amended bill text loses the per-amendment contribution and prevents the scoring engine from differentiating between a member's vote on the amendment vs their vote on final passage.

## Architectural Decision: Lightweight Decomposition + Multi-Pass Analysis

**Per Q29 of planning, amendments DO go through a lightweight decomposition step before LLM analysis** — local semantic chunking + theme extraction, mirroring the bill-side decomposition principle (§10.4) at smaller scale. Earlier drafts of this area had amendments skip decomposition entirely; **reversed** because:

- LLMs benefit from being given pre-organized themes/sections vs raw concatenated text. Multi-policy-change amendments dilute focus when fed as a wall of text.
- Symmetry with bills: bills decompose → cluster → simplify → analyze. Amendments now follow the same shape, just lighter.
- Significance scoring (per Q30) needs theme references — findings tied to themes give the stance materializer structured evidence to weight.

**Lighter than bill decomposition** — amendments do NOT get the Haiku-simplification step from §10.4. Amendment text is short enough that per-cluster simplification doesn't add value beyond what the analysis prompt already produces. The pipeline:

```
amendment_text_chunks (already embedded with 384-dim vectors by §7.6 via DJL)
    ↓
AmendmentDecompositionService:
  - Smile k-means with FIXED SEED (Q36 = 42, deterministic for tests)
  - k determined dynamically via silhouette score (Q34 — try k=1..5, pick best)
  - Top-TF-IDF terms per cluster generate the theme label (Q35 — pure-local, no LLM)
  - Persist amendment_themes + amendment_theme_chunk_members (Q47 — join table, not BIGINT[])
    ↓ produces 1–5 themes per text version
LLM Pass 1 (Haiku): structured input = full text + theme summaries (themes in order with chunk excerpts)
    ↓ emits findings (each tagged with impact: FindingImpact + theme reference) AND complexityLevel: AnalysisComplexity
    ↓ NO finding count cap (Q38 — trust the model). Watch outliers in observability.
LLM Pass 2 (Sonnet) on escalation — same structured input
LLM Pass 3 (Opus) on further escalation — same structured input
    ↓ each pass writes amendment_findings rows
```

Bills retain full decomposition with Haiku simplification (§10.4 unchanged). Amendments take the lighter clustering-only path.

### `AmendmentDecompositionService[F[_]: Sync]`

```scala
class AmendmentDecompositionService[F[_]: Sync](
  textChunkRepo:  AmendmentTextChunkRepository[F],
  themeRepo:      AmendmentThemeRepository[F],
  config:         AmendmentDecompositionConfig
)

case class AmendmentDecompositionConfig(
  seed:       Long = 42L,    // Q36 — fixed for determinism. Change later if scoring needs randomized clustering
  maxThemes:  Int  = 5,      // Q34 — silhouette tries k=1..maxThemes
  topNTerms:  Int  = 3       // Q35 — TF-IDF tokens per theme label
)
```

| Function | Signature | Behavior |
|---|---|---|
| `cluster` | `(textVersionId: Long) => F[List[AmendmentThemeDO]]` | (1) Fetch chunks via `textChunkRepo.findByVersionId(versionId)`. (2) Build embedding matrix. (3) For k = 1..config.maxThemes: run Smile `KMeans.fit(embeddings, k = k, seed = config.seed)` and compute silhouette score. (4) Pick the k with best silhouette. (5) For each cluster: compute centroid embedding, generate label via `topTfIdfTerms`. (6) Persist `amendment_themes` rows + `amendment_theme_chunk_members` rows in one transaction. (7) Return persisted DOs. |
| `topTfIdfTerms` (private) | `(clusterChunks: List[String], corpus: List[String], topN: Int) => String` | Compute TF-IDF for each token. Pick top N by score, lowercase, join with hyphens, e.g. `"highway-funding-restriction"`. Stop-word filtered. |

**Why multi-pass routing (unchanged):**
- Amendments vary widely in complexity. A "Strike subsection (a)(2)" trivial edit needs only Haiku. A 50-page substitute amendment needs Sonnet or Opus.
- **Pass 1 (Haiku) on every amendment** produces findings AND a complexity assessment. Pass 2/3 escalation is gated on that complexity (Q27: trust Sonnet's complexity over Haiku's once Sonnet runs).

## Multi-Pass Routing

```
amendment.text.ingested arrives
    |
    v
AmendmentAnalysisOrchestrator.analyze(amendmentId, versionId, correlationId)
    |
    v
AmendmentDecompositionService (per Q29):
    Read amendment_text_chunks for this version
    Smile k-means cluster on chunk embeddings → 1–5 themes
    Persist amendment_themes rows
    │
    v
Pass 1 (ALWAYS): Haiku
    LLM input: full amendment text + theme summaries (each theme has a label + chunk excerpts)
    LLM output: AmendmentPassOutput {
      findings: List[AmendmentFindingItem],         // each carries impact: FindingImpact (per Q30)
      complexityLevel: Option[AnalysisComplexity], // TRIVIAL..SPRAWLING. Required on Pass 1 + Pass 2; None on Pass 3
      complexityRationale: Option[String]            // model's free-text justification
    }
    Persist findings as AmendmentFindingDO rows with passNumber=1, theme_id, impact
    Persist complexity to amendment_complexity_scores with passNumber=1
    │
    v
AmendmentPassRouter.shouldEscalate(haikuComplexityLevel, config):
    < config.pass2Threshold (default AnalysisComplexity.Standard) → STOP. Pass 1 alone.
    >= config.pass2Threshold                                       → Run Pass 2.
    │
    v
Pass 2 (CONDITIONAL): Sonnet
    Same input. SAME output schema — Sonnet ALSO emits a complexityLevel.
    Persist findings with passNumber=2.
    Persist complexity to amendment_complexity_scores with passNumber=2.
    Pass 1 findings retained alongside Pass 2 (evidence trail + tier comparison).
    │
    v
AmendmentPassRouter.shouldEscalateFurther(sonnetComplexityLevel, config):
    < config.pass3Threshold (default AnalysisComplexity.Intricate) → STOP. Passes 1+2.
    >= config.pass3Threshold                                        → Run Pass 3.
    │
    v
Pass 3 (RARE): Opus
    Same input. Output: findings only (Opus is terminal — no complexityLevel).
    Persist findings with passNumber=3. NO complexity row inserted for Pass 3.
    │
    v
Emit AnalysisCompletedEvent(entityType="amendment", entityId=amendmentId,
                             passesRun=passNumbers, correlationId=correlationId)
```

> **Why Sonnet also emits a complexity level** (per Q27 of planning): Sonnet sees the amendment text more carefully than Haiku and may identify nuance Haiku missed — e.g., a substitute amendment Haiku rates `Standard` might actually be `Sprawling` once Sonnet reads the cross-references. **Sonnet's complexity level (NOT Haiku's) gates Pass 3 escalation.** Amendments that Haiku rates near the Pass 2 threshold can avoid Opus if Sonnet confirms they're not that complex; amendments Haiku underestimates can still escalate if Sonnet flags them.

> **Why textual `AnalysisComplexity` instead of numeric score** (per Q28 of planning): the LLM picks from a fixed enum vocabulary (TRIVIAL / ROUTINE / STANDARD / INVOLVED / INTRICATE / SPRAWLING) instead of free-form 0.0–1.0 numbers. Eliminates out-of-range values (model can't emit `1.5`), reads cleaner in observability ("escalated because Sonnet rated it INTRICATE"), and produces a discrete histogram for tuning. Per Q56 — the routing-input vocabulary deliberately differs from the per-finding `FindingImpact` vocabulary (NEGLIGIBLE..PIVOTAL) so meaning is clear at every read site.

> **Pass 3 (Opus) is terminal** — no further escalation. No complexityLevel emitted by Opus.

> **Threshold tuning:** `pass2Threshold = Standard` and `pass3Threshold = Intricate` are starting defaults — Sonnet runs on amendments at Standard or above; Opus runs on Intricate or above. `AnalysisComplexity.Ordering` orders the levels Trivial < Routine < Standard < Involved < Intricate < Sprawling. Real values get tuned from production data — query `amendment_complexity_scores GROUP BY complexity_level` for distribution and validate escalation rate.

## New Class: `AmendmentAnalysisOrchestrator[F[_]]`

```scala
class AmendmentAnalysisOrchestrator[F[_]: Async](
  haikuProvider: LlmProvider[F],
  sonnetProvider: LlmProvider[F],
  opusProvider: LlmProvider[F],
  passRouter: AmendmentPassRouter,
  promptAssembler: AmendmentPromptAssembler,            // analog to BillPromptAssembler from Component 8
  embeddingService: SemanticEmbeddingService[F],
  findingPersister: AmendmentFindingPersister[F],
  amendmentTextRepo: AmendmentTextVersionRepository[F],
  amendmentTextChunkRepo: AmendmentTextChunkRepository[F],
  config: AmendmentAnalysisConfig,
  logger: PipelineLogger[F]
)
```

| Function | Signature | Behavior |
|---|---|---|
| `analyze` | `(amendmentId: Long, versionId: Long, correlationId: UUID) => F[AmendmentAnalysisResult]` | (1) Reuse check: `complexityScoreRepo.versionAlreadyAnalyzed(amendmentId, versionId)` — if true return `AlreadyAnalyzed`. (2) **Decompose** (per Q29): `decompositionService.cluster(versionId)` produces 1–5 themes, persisted to `amendment_themes`. (3) Fetch full text: `amendmentTextChunkRepo.findByVersionId(versionId)`. (4) **Fetch parent-amendment context** (per Q52): if `amendment.parentAmendmentId.isDefined`, fetch the parent's most-recent text version + its findings as background context for the LLM prompt. Recurse one level only — the parent's parent isn't fetched (token-budget concern). (5) **Pass 1 (Haiku)**: `executePass(text, themes, parentContext, haikuProvider, passNumber=1)` → returns `AmendmentPassOutput`. (6) `passRouter.shouldEscalate(...)` → if true: **Pass 2 (Sonnet)**. (7) `passRouter.shouldEscalateFurther(...)` → if true: **Pass 3 (Opus)** with `expectsComplexity=false`. (8) Emit `AnalysisCompletedEvent`. |
| `executePass` (private) | `(text: String, themes: List[AmendmentThemeDO], provider: LlmProvider[F], passNumber: Int, expectsComplexity: Boolean = true) => F[AmendmentPassOutput]` | Build `LlmRequest` with text + theme summaries injected as structured context. Call `provider.completeStructured[AmendmentPassOutput](request)`. For each finding: generate embedding, **resolve `theme_id` via embedding cosine similarity (per Q37)** — embed the LLM-emitted `themeReference` string, find the closest-matching `theme.embedding` above similarity threshold (default 0.7). If no theme matches above threshold, set `theme_id = NULL`. Then build `AmendmentFindingDO` with `passNumber`, `theme_id`, `impact: FindingImpact`, persist via `findingPersister.insert`. **If `expectsComplexity` is true** (Pass 1 + Pass 2): persist `AmendmentComplexityScoreDO`. **Pass 3 sets `expectsComplexity=false`**. |

> **Why `versionAlreadyAnalyzed` checks `amendment_complexity_scores`, not `amendment_findings`** (per Q5 of planning): Pass 1 may legitimately produce zero findings on trivial amendments (e.g., "strike subsection (a)") while still emitting a complexity score (likely very low). Checking `amendment_findings` only would miss this case — re-running Pass 1 on every event re-delivery wastes Haiku calls. The complexity score is written even when findings is empty, so it's the more-reliable "we ran something for this version" signal.
>
> ```sql
> SELECT EXISTS (
>   SELECT 1 FROM amendment_complexity_scores
>   WHERE amendment_id = $amendmentId AND version_id = $versionId
> );
> ```
>
> Pass 3 (Opus) doesn't write a complexity row, but it only runs after Pass 1 + Pass 2, and Pass 1 always writes a complexity row. So if Pass 1 ran for this version, the row exists.

### `AmendmentPassRouter`

Pure decision logic, mirrors `PassRouter` for bills (§10.6) but per-amendment instead of per-concept-group.

```scala
class AmendmentPassRouter(config: AmendmentPassRoutingConfig)

  def shouldEscalate(level: AnalysisComplexity): Boolean =
    level.rank >= config.pass2Threshold.rank

  def shouldEscalateFurther(level: AnalysisComplexity): Boolean =
    level.rank >= config.pass3Threshold.rank
```

```scala
case class AmendmentPassRoutingConfig(
  pass2Threshold: AnalysisComplexity = AnalysisComplexity.Standard,    // Pass 2 (Sonnet) escalates at Standard or higher
  pass3Threshold: AnalysisComplexity = AnalysisComplexity.Intricate    // Pass 3 (Opus) escalates at Intricate or higher
)
```

Configurable via `application.conf` — operator can disable Pass 2/3 entirely by setting threshold `> 1.0`.

### `AmendmentPassOutput` — LLM structured output

```scala
case class AmendmentPassOutput(
  findings: List[AmendmentFindingItem],
  complexityLevel: Option[AnalysisComplexity],  // TRIVIAL..SPRAWLING per Q28. Required on Pass 1 + Pass 2. None on Pass 3 (Opus is terminal)
  complexityRationale: Option[String]            // Free-text justification — logged + persisted with the score row
)

case class AmendmentFindingItem(
  findingTypeCode: String,           // looked up to finding_types.id
  themeReference:  Option[String],   // per Q29 — references the theme label this finding most relates to. NULL when finding spans multiple themes
  summary: String,
  details: Option[String],
  severity: Option[String],          // "low" | "medium" | "high"
  impact: FindingImpact,             // per Q30 — NEGLIGIBLE..PIVOTAL. How impactful is THIS finding for stance scoring weight (per Q56 — distinct vocabulary from complexity routing input)
  confidence: Option[Double],        // 0.0–1.0. Model's confidence in the finding (kept numeric — orthogonal to impact)
  affectedSection: Option[String]    // free-text reference to part of the amendment, e.g. "Section 2(a)"
)
```

> **Why the same output schema across passes:** the prompt assembler (Component 8) issues a different system prompt per tier. Haiku and Sonnet prompts request `findings` (with `impact`) + `complexityLevel` + `complexityRationale`. Opus prompt requests `findings` only with `complexityLevel=null`. Same Circe-derived schema for all three; the orchestrator dispatches on `expectsComplexity` to decide which fields to require.

### `AmendmentPromptAssembler` (Component 8 extension)

A new prompt profile in Component 8's GCS prompt block storage: `amendment-analysis-{tier}.md` where tier is `haiku` / `sonnet` / `opus`. Haiku and Sonnet prompts include:

> "Cluster the findings by theme using the labels provided in the input. For each finding, pick an `impact` level from: NEGLIGIBLE, MINOR, NOTABLE, SUBSTANTIAL, MAJOR, PIVOTAL — based on how impactful the finding would be on legislator stance scoring. After identifying findings, assess the overall complexity of this amendment by picking a `complexityLevel` from this distinct vocabulary: TRIVIAL, ROUTINE, STANDARD, INVOLVED, INTRICATE, SPRAWLING. The two enums use deliberately different words so the model and reviewers don't conflate per-finding impact with per-amendment complexity. Consider for `complexityLevel`: amendment length, number of distinct policy changes, breadth of impact, presence of substitute language, cross-references to other statutes."

Opus prompt requests findings only and instructs `complexityLevel=null`.

## Schema additions

**Three new tables** — `amendment_themes` (decomposition output), `amendment_findings` (analysis output), `amendment_complexity_scores` (routing input). All denormalized per Q7, no JSONB.

```sql
-- Per Q56 — two distinct enums so meaning is clear at every read site.
-- analysis_complexity = per-amendment / per-bill routing input ("how complex to analyze?")
-- finding_impact      = per-finding stance-scoring weight ("how much does this finding move the score?")
CREATE TYPE analysis_complexity AS ENUM (
  'TRIVIAL', 'ROUTINE', 'STANDARD', 'INVOLVED', 'INTRICATE', 'SPRAWLING'
);

CREATE TYPE finding_impact AS ENUM (
  'NEGLIGIBLE', 'MINOR', 'NOTABLE', 'SUBSTANTIAL', 'MAJOR', 'PIVOTAL'
);

-- Per Q29: lightweight semantic clustering output. 1–5 themes per text version.
CREATE TABLE amendment_themes (
  id                BIGSERIAL PRIMARY KEY,
  amendment_id      BIGINT NOT NULL REFERENCES amendments(id) ON DELETE CASCADE,
  text_version_id   BIGINT NOT NULL REFERENCES amendment_text_versions(id) ON DELETE CASCADE,
  label             TEXT NOT NULL,                        -- top-TF-IDF label per Q35, e.g. "highway-funding-restriction" — pure-local generation, no LLM
  embedding         vector(384) NOT NULL,                 -- centroid embedding of clustered chunks
  ordering          SMALLINT NOT NULL,                    -- display/processing order, 0-indexed
  created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (text_version_id, ordering)
);

CREATE INDEX amendment_themes_amendment_id_idx ON amendment_themes(amendment_id);
CREATE INDEX amendment_themes_version_idx ON amendment_themes(text_version_id);

-- Per Q47 — join table replaces `chunk_member_ids BIGINT[]` array column.
-- Cleaner Doobie integration (no array codec needed) + compatible with the no-JSONB rule.
CREATE TABLE amendment_theme_chunk_members (
  theme_id  BIGINT NOT NULL REFERENCES amendment_themes(id) ON DELETE CASCADE,
  chunk_id  BIGINT NOT NULL REFERENCES amendment_text_chunks(id) ON DELETE CASCADE,
  PRIMARY KEY (theme_id, chunk_id)
);

CREATE INDEX amendment_theme_chunk_members_chunk_idx ON amendment_theme_chunk_members(chunk_id);
```

> **Doobie codec support note (per Q47):** The join-table approach avoids needing a Postgres `BIGINT[]` codec. Existing repo uses Doobie auto-derived `Read`/`Write` on case classes — every column maps cleanly to a primitive scala type. Two-row case class for `AmendmentThemeChunkMemberDO(themeId: Long, chunkId: Long)` works without custom codecs.

```sql
CREATE TABLE amendment_findings (
  id                   BIGSERIAL PRIMARY KEY,
  amendment_id         BIGINT NOT NULL REFERENCES amendments(id) ON DELETE CASCADE,
  text_version_id      BIGINT NOT NULL REFERENCES amendment_text_versions(id) ON DELETE CASCADE,  -- per Q8: which version's text produced this finding
  theme_id             BIGINT REFERENCES amendment_themes(id) ON DELETE SET NULL,  -- per Q29: theme this finding relates to. NULL when finding spans multiple themes / can't be tied to one
  finding_type_id      INTEGER NOT NULL REFERENCES finding_types(id),
  pass_number          SMALLINT NOT NULL,                  -- 1 | 2 | 3
  summary              TEXT NOT NULL,
  details              TEXT,
  severity             TEXT,                                -- "low" | "medium" | "high" | NULL
  impact               finding_impact NOT NULL,             -- per Q30: per-finding weight for stance materialization. LLM emits this on each finding (NEGLIGIBLE..PIVOTAL)
  confidence           DOUBLE PRECISION,                    -- 0.0–1.0 or NULL — model's confidence (different from impact)
  affected_section     TEXT,                                -- free-text e.g. "Section 2(a)"
  embedding            vector(384),                         -- pgvector for semantic search across findings
  llm_model            TEXT NOT NULL,                       -- "claude-haiku-4-5" / "claude-sonnet-4-6" / "claude-opus-4-7"
  analyzed_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  CONSTRAINT amendment_findings_uniq UNIQUE (amendment_id, text_version_id, pass_number, finding_type_id, summary)
);

CREATE INDEX amendment_findings_text_version_idx ON amendment_findings(text_version_id);
CREATE INDEX amendment_findings_theme_idx ON amendment_findings(theme_id) WHERE theme_id IS NOT NULL;
CREATE INDEX amendment_findings_impact_idx ON amendment_findings(impact);

CREATE INDEX amendment_findings_amendment_id_idx ON amendment_findings(amendment_id);
CREATE INDEX amendment_findings_finding_type_idx ON amendment_findings(finding_type_id);
CREATE INDEX amendment_findings_pass_number_idx ON amendment_findings(amendment_id, pass_number);
CREATE INDEX amendment_findings_embedding_idx ON amendment_findings USING ivfflat (embedding vector_cosine_ops);

-- NEW: dedicated complexity-scoring table per user direction.
-- One row per (amendment, version, pass) for passes that emit a complexity score (Pass 1 + Pass 2).
-- Pass 3 (Opus) does NOT write to this table — it's terminal, no further routing.
-- Per Q28: textual AnalysisComplexity, NOT numeric. LLM picks from 6 fixed values.
CREATE TABLE amendment_complexity_scores (
  id                   BIGSERIAL PRIMARY KEY,
  amendment_id         BIGINT NOT NULL REFERENCES amendments(id) ON DELETE CASCADE,
  version_id           BIGINT NOT NULL REFERENCES amendment_text_versions(id) ON DELETE CASCADE,
  pass_number          SMALLINT NOT NULL,                  -- 1 (Haiku) | 2 (Sonnet); NEVER 3
  complexity_level     analysis_complexity NOT NULL,       -- TRIVIAL | ROUTINE | STANDARD | INVOLVED | INTRICATE | SPRAWLING (per Q28)
  complexity_rationale TEXT,
  llm_model            TEXT NOT NULL,
  scored_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (amendment_id, version_id, pass_number)
);

CREATE INDEX amendment_complexity_amendment_id_idx ON amendment_complexity_scores(amendment_id);
CREATE INDEX amendment_complexity_level_idx ON amendment_complexity_scores(complexity_level);  -- for histogram / threshold-tuning queries
```

`Tables.AmendmentFindings()` already exists in pipeline-models 0.1.21. **NEW**: `Tables.AmendmentComplexityScores()` constant added to pipeline-models per [P7.5](../07-amendments-pipeline/PRODUCTION_TASKS.md).

## How Component 11 §11.12 picks which pass's findings to use

When `materializeAmendmentStances(amendment)` reads findings to feed into the stance LLM:

```scala
val highestPassFindings: List[AmendmentFindingDO] = findingPersister.findByAmendmentId(amendment.id)
  .map { all =>
    val maxPass = all.map(_.passNumber).maxOption.getOrElse(1)
    all.filter(_.passNumber == maxPass)
  }
```

The highest-pass findings represent the best-available analysis. Lower-pass findings are kept in the table for evidence-trail and tuning purposes but are not used for scoring. This is consistent with how bill-side scoring uses Pass 3 findings when available, falling back to Pass 2 then Pass 1.

## Re-analysis triggers

Amendment analysis runs when:

1. `amendment.text.ingested` arrives — initial analysis after first text version.
2. New `amendment_text_versions` row arrives for the same amendment (e.g., a "Modified" version after a "Submitted") → `amendment.text.ingested` fires again with the new versionId, full multi-pass analysis runs against the new version.

Bill analysis triggers are **unchanged**.

## Sub-amendment parent context (per Q52)

When `amendment.parentAmendmentId.isDefined`, the analysis orchestrator fetches the **immediate parent's** text + findings as background context for the LLM:

```scala
parentContext: Option[ParentContext] = amendment.parentAmendmentId.traverse { parentId =>
  for {
    parentVersion  <- textVersionRepo.findLatestByAmendmentId(parentId)
    parentFindings <- findingPersister.findByAmendmentId(parentId)
  } yield ParentContext(parentVersion, parentFindings)
}
```

Pass 1/2/3 LLM prompts include the parent's most-recent text + findings as a "Background: this is a sub-amendment of X. Here's what X does and what we found about X." section.

**One-level recursion only** — grandparent context is NOT fetched. Token-budget consideration. Per Q52: "engineer around cost when implementing. But initially work naively around that cost" — naive single-level walk is the initial implementation. Stage deeper recursion as a follow-up if scoring quality demands it.

Cost impact: sub-amendments incur ~30-50% larger prompts (parent text + findings as context). Pass 1 cost goes up correspondingly. Watch `amendment_text_chunk_count_avg` for sub-amendments specifically in observability.
