# Area 11.12 — Amendment Scoring Integration

> Project: `stance-materializer` + `scoring-pipeline` | Package additions
> **Driven by**: Component 7 §7.4 (votes-pipeline records amendment-typed roll calls), Component 7 §7.6 (amendment text ingested), Component 10 §10.11 (`amendment_findings` populated)
> **Status**: Net-additions to existing scoring pipelines, not new projects

## Purpose

Amendment-typed roll-call votes (`votes.legislation_type ∈ {HAMDT, SAMDT, SUAMDT}`) currently flow through `votes-pipeline` (per §7.4) but receive **no scoring contribution** because:

1. `member_bill_stances` keys on `bill_id`, but amendment-typed votes have `bill_id IS NULL`.
2. `member_bill_stance_topics` is populated by §11.9 from `bill_findings`, not `amendment_findings`.

Result: a member's vote on a substantive amendment is invisible to alignment scoring. This area closes that gap.

**Why this matters:** votes on amendments are often the most policy-revealing signal in a member's voting record — final passage votes are frequently along party lines, while amendment votes split caucuses on substantive policy questions. Without amendment-vote scoring, alignment scores miss the highest-signal data.

## Architectural Decision: Bill-Driven Amendment Scan (per Q8)

**Decision:** the stance materializer (§11.9) processes amendments **inline when it processes their parent bill**. There is **no separate `amendment_materialization_status` table**, no separate `findReadyAmendments` scan, no separate event flow.

When §11.9 picks a ready bill from `stance_materialization_status`, it:
1. Materializes the bill's stances (existing path).
2. Scans `amendments WHERE bill_id = $billId` (returns the bill's amendments).
3. For each amendment that has **both votes AND findings**:
   - Has-votes check: `EXISTS (SELECT 1 FROM votes WHERE legislation_type IN ('HAMDT','SAMDT','SUAMDT') AND legislation_number = amendments.number AND congress = amendments.congress)`
   - Has-findings check: `EXISTS (SELECT 1 FROM amendment_findings WHERE amendment_id = amendments.id)`
   - If both true → materialize the amendment's stances inline.

This eliminates the need for cross-pipeline writes to a status table — scoring works off the source-of-truth tables directly. Standalone amendments (where `amendments.bill_id IS NULL`) are not currently materialized; they would require a separate trigger if downstream needs them. Defer until concrete need.

## Stance Materializer Extension (§11.9 changes)

`StanceMaterializer.materializeBill(billId)` now ends with an inline amendment-materialization phase that includes both **direct** amendments (FK = bill_id) **AND sub-amendments** transitively reachable via `parent_amendment_id` chains (per user direction this turn):

```scala
def materializeBill(billId: Long): F[MaterializationResult] = for {
  // 1. Existing bill materialization
  billResult <- existingMaterializeBillBody(billId)

  // 2. NEW — fan out to all amendments (direct + transitive sub-amendments).
  //    Simple WHERE on the denormalized effective_bill_id column (per §7.2).
  amendments <- amendmentRepo.findByEffectiveBillId(billId)
  amendmentResults <- amendments.parTraverse { amendment =>
    for {
      hasVotes    <- voteRepo.existsForAmendment(
                        congress = amendment.congress,
                        amendmentType = amendment.amendmentType.getOrElse(throw …),
                        number = amendment.number)
      hasFindings <- amendmentFindingRepo.existsForAmendment(amendment.id)
      result <- if (hasVotes && hasFindings) {
        materializeAmendmentStances(amendment).map(Some.apply)
      } else {
        Sync[F].pure(None)  // skip — not yet ready, will be picked up by backfill scanner
      }
    } yield result
  }
} yield MaterializationResult(
  billId = billId,
  membersProcessed = billResult.membersProcessed,
  topicRowsCreated = billResult.topicRowsCreated,
  amendmentsMaterialized = amendmentResults.flatten.size
)
```

**`AmendmentRepository.findByEffectiveBillId(billId: Long): F[List[AmendmentDO]]`** — defined in §7.2. SQL (with the Q24 NULL-filter):

```sql
SELECT id, natural_key, congress, amendment_type, number, bill_id, parent_amendment_id, effective_bill_id, ...
FROM amendments
WHERE effective_bill_id = $billId
  AND update_date IS NOT NULL;   -- Q24: skip unhydrated placeholders
```

For a bill with 3 direct amendments and 2 sub-amendments under one of them: all 5 rows have `effective_bill_id = bill.id` (the direct ones because `bill_id` matches; the sub-amendments because §7.3's resolution sweep populated it). Single SELECT, no recursion at query time. Recursion only happens once at ingest (in §7.3) when populating the cache.

`materializeAmendmentStances(amendment: AmendmentDO)` is the new private method that mirrors the bill stance materialization:
1. Fetch all member votes on this amendment via `voteRepo.findByLegislation(congress, amendmentType, number)`.
2. **Per vote, resolve the active text version at the time of the vote** (per Q8 + Q43 — track version-as-voted-on, with EARLIEST-version fallback when vote pre-dates publication):
   ```sql
   SELECT id FROM amendment_text_versions
   WHERE amendment_id = $amendmentId
     AND (published_date IS NULL OR published_date <= $voteDate)
   ORDER BY published_date DESC NULLS LAST
   LIMIT 1
   -- If above returns NULL (vote pre-dates all known publication dates per Q43),
   -- fall back to the EARLIEST available text version:
   SELECT id FROM amendment_text_versions
   WHERE amendment_id = $amendmentId
   ORDER BY published_date ASC NULLS LAST
   LIMIT 1
   ```
   If multiple versions exist (Submitted at T0 + Modified at T1) and a vote happened at T2 where `T0 < T1 < T2`, the active version is "Modified". A vote at T2' where `T0 < T2' < T1` uses "Submitted". A vote at T-pre where `T-pre < T0` uses "Submitted" anyway via the fallback (vote happened before CREC publication, but the amendment's content existed — CREC is the publication record, not the moment of submission). This `text_version_id` gets stored on the `member_amendment_stances` row for traceability.
3. **Fetch ALL findings for the amendment** via `amendmentFindingRepo.findByAmendmentId(amendment.id)` — **NOT** filtered by version (per Q14). The LLM sees the full evolution as evidence.
4. **Per-topic dedup across passes** (per Q40): group findings by topic, take the highest-pass-number finding within each topic (Opus > Sonnet > Haiku). Lower-pass findings on the same topic are dropped from this pass's evidence — they're still in the table for diagnostic queries, but the LLM sees one canonical finding per topic per amendment.
5. **Weight findings by impact** (per Q30): each finding carries an `impact: FindingImpact` (NEGLIGIBLE..PIVOTAL). The stance LLM prompt presents findings ordered by impact descending, tagged with their level. **Per-topic algorithmic alignment-score contributions also weight by impact** — a PIVOTAL finding pulls the legislator's per-topic score harder than a NEGLIGIBLE one. Impact-weight mapping is **stored in the `finding_impact_weights` DB table** (per Q48 — system-wide setting, not per-application config), initialized to:
   ```
   NEGLIGIBLE  → 0.1
   MINOR       → 0.3
   NOTABLE     → 0.5
   SUBSTANTIAL → 0.7
   MAJOR       → 1.0
   PIVOTAL     → 1.5
   ```
   Score calculator queries the table at startup, caches the mapping in memory. Operator updates the table via SQL to retune across the entire system.
6. For each (member, vote) pair: build `StanceReasoningOutput` LLM call with the deduplicated finding evidence, plus:
   - **The vote outcome from `votes.result`** (verified field — `Option[String]` like `"Passed"`, `"Failed"`, `"Agreed to"`, etc.) as **background context** per Q31 + Q42. NOT as a stance modifier — performative votes count fully; LLM instructed not to discount stance based on outcome.
   - The active text_version_id at vote time (per Q8 + Q43 — version-as-voted-on with earliest-fallback).
   - **Abstention handling per Q41**: if `vote_cast` is `NotVoting` or `Present`, materialize a stance row with `stance_direction = Neutral` for each topic. The member was present-but-uncommitted. Counts as data, not as a Yes/No signal.
7. Persist results to `member_amendment_stances` (with `text_version_id` populated) + `member_amendment_stance_topics`. **Each topic row links to its supporting findings via the `member_amendment_stance_topic_findings` join table** (per Q44 — many-to-many, not singular FK). Multiple findings on the same topic each get a join row.

> **Why all findings, not just version-active-at-vote** (per Q14): a member's vote may reflect knowledge of the amendment's full history — they may have opposed an earlier "Submitted" version that was later weakened by "Modified." Filtering to only the version-active-at-vote loses that signal. The LLM gets the full evidence and weights it appropriately. The `text_version_id` linkage on the stance row tells downstream consumers which version the vote-as-cast was *technically against*, but the analytical context is the full evolution.

> **Why fan-out is parTraverse:** amendments per bill are typically <10. Sequential would be fine but parTraverse is cheap on this scale and matches the existing parallelism conventions.

> **Idempotency:** if an amendment is materialized this run but its parent bill is reprocessed later, the unique constraint `(member_id, amendment_id, vote_id)` prevents duplicates. Re-running materialization just upserts.

> **What if a bill has no amendments?** `findByBillId` returns empty; the parTraverse is a no-op; amendment materialization adds zero overhead to the bill path.

> **What if an amendment has votes but no findings yet** (or vice versa)? Skipped this run. The amendment will be picked up by the **backfill scanner** (next section) once both inputs land, OR the next time the parent bill is naturally re-materialized.

## Amendment Backfill Scanner

The bill-driven materializer in §11.9 only fans out to amendments **when the parent bill is being processed**. That means an amendment whose votes and findings arrive AFTER the parent bill's last materialization sits in a "ready but un-materialized" state until the bill is re-materialized for some other reason. For most amendments this lag is fine (next dirty-bill cycle picks it up), but a backfill scanner closes the gap explicitly.

### Class: `AmendmentBackfillScanner[F[_]]`

Lives alongside §11.9 in `stance-materializer`. Constructor: `(amendmentRepo, voteRepo, amendmentFindingRepo, materializer, logger, xa)`.

| Function | Signature | Behavior |
|---|---|---|
| `findReadyAmendments` | `() => F[List[(Long, Long)]]` | Returns `(amendmentId, billId)` pairs for amendments that have votes AND findings AND no `member_amendment_stances` rows AND a non-NULL `bill_id`. SQL below |
| `backfillAmendments` | `() => F[List[BackfillResult]]` | For each pair, invoke `materializer.materializeBill(billId)` — the existing `materializeBill` flow naturally fans out to the amendment via `findByBillId` and picks it up. **Re-uses the existing path; no new materialization code.** |

### Backfill query — simple thanks to denormalized `effective_bill_id`

§7.3 maintains `amendments.effective_bill_id` as a denormalized cache (eager resolution at ingest + end-of-run sweep). That makes the backfill query a simple WHERE clause — no recursive CTE at scoring time. **Per Q24 of planning, the query also filters out amendments with NULL required-field values** to exclude unhydrated placeholders (e.g. votes-pipeline created a placeholder but amendments-pipeline never returned a Detail for it):

```sql
SELECT a.id AS amendment_id, a.effective_bill_id
FROM amendments a
WHERE a.effective_bill_id IS NOT NULL                    -- excludes treaty / procedural / pending-resolution
  -- Q24: ensure the amendment is hydrated (not a stale placeholder).
  -- update_date is the canonical "we have real Congress.gov data" signal —
  -- placeholders have it NULL until hydration. Sponsor / chamber / amendment_type
  -- are all NULL on placeholders too; checking update_date is sufficient since hydration
  -- always populates it.
  AND a.update_date IS NOT NULL
  AND EXISTS (
      SELECT 1 FROM votes v
      WHERE v.legislation_type IN ('HAMDT', 'SAMDT', 'SUAMDT')
        AND v.legislation_number = a.number
        AND v.congress = a.congress
    )
  AND EXISTS (SELECT 1 FROM amendment_findings af WHERE af.amendment_id = a.id)
  AND NOT EXISTS (
      SELECT 1 FROM member_amendment_stances mas
      WHERE mas.amendment_id = a.id
    )
ORDER BY a.effective_bill_id   -- group by bill so each materializeBill call drains all of that bill's amendments at once
LIMIT $batchSize;
```

> **The same `update_date IS NOT NULL` guard applies to all read-side amendment queries used by scoring** (per Q24): `findByEffectiveBillId`, the §11.2 union of amendment stances, the §11.3 weight calculation lookups. Anywhere a query enumerates amendments for scoring purposes, filter `update_date IS NOT NULL` to exclude orphan placeholders. The placeholder rows still exist in `amendments` for vote-pipeline FK / linkage purposes — they just don't participate in scoring.

**Why this is simpler than the earlier draft:** the recursive parent-chain walk happens at amendments-pipeline ingest time (§7.3) and lives on the row. The scoring side just reads `effective_bill_id` like any other FK column. Sub-amendments and direct amendments are indistinguishable from the backfill scanner's perspective — both have `effective_bill_id` populated and get materialized the same way.

**Triggering materialization:** the scanner calls `materializeBill(effective_bill_id)` per ready bill. The existing `materializeBill` fan-out via `findByEffectiveBillId(billId)` (also a simple WHERE clause now — see below) picks up all amendments + sub-amendments belonging to that bill in one query. No recursion at scoring time.

> **Why backfill triggers `materializeBill(billId)` rather than calling `materializeAmendmentStances(amendment)` directly**: re-using `materializeBill` keeps the materialization logic in one path. If multiple amendments share a parent bill, one `materializeBill` call covers all of them via the existing fan-out. The bill's own stances are re-materialized too — that's idempotent (unique constraint on `(member_id, bill_id, vote_id)` in `member_bill_stances` prevents duplicates) and acceptable cost.

### Schedule

The backfill scanner runs as a separate Ofelia job at a slower cadence than the main stance materializer:

```ini
[job-run "amendment-backfill"]
schedule = 0 0 * * *      ; Once daily at midnight
container = stance-materializer
command = ["scala-runner", "--run", "amendment-backfill"]
```

The same `stance-materializer` container exposes both `materialize` (default cron) and `amendment-backfill` (subcommand) entry points. Daily cadence is chosen because the lag tolerance for amendment scoring is roughly "next day" — high-frequency amendments getting analyzed will already be picked up by the natural bill-driven path.

## Why amendments may have `bill_id IS NULL` (skipped from materialization)

The backfill scanner WHERE clause excludes `bill_id IS NULL` amendments. This is deliberate. Amendments lack a parent bill in the API for three legitimate reasons (per [LoC AmendmentEndpoint.md](https://github.com/LibraryOfCongress/api.congress.gov/blob/main/Documentation/AmendmentEndpoint.md)):

| Case | What it means | Frequency | Scoring path |
|------|--------------|-----------|--------------|
| **Sub-amendment** (amendment-amends-amendment) | The amendment modifies *another amendment*, not a bill directly. The detail response has `amendedAmendment` populated instead of `amendedBill`. §7.3 stores `parent_amendment_id` linkage. The chain `subAmendment → parentAmendment → ... → bill` may be 1+ levels deep | Common during conference committees and amendment trees on major appropriations / reconciliation bills | **Scored** (per user direction this turn) — backfill scanner walks `parent_amendment_id` recursively to find effective bill, then triggers `materializeBill(effective_bill_id)`. `findAllForBillTransitive` picks up sub-amendments via the same recursion |
| **Treaty amendment** (`amendedTreaty` populated, no `amendedBill`, no `amendedAmendment`) | The amendment modifies a treaty submitted to the Senate for ratification. Treaties have their own scoring path that doesn't exist yet (RepCheck doesn't ingest treaties as of MVP) | Rare — treaty traffic is low | **Permanently skipped** unless treaty ingestion lands as its own component. Not on roadmap |
| **Procedural / orphaned** | No `amendedBill`, no `amendedAmendment`, no `amendedTreaty`. Either malformed upstream data, or a procedural amendment to chamber rules that doesn't reference any underlying instrument | Very rare per upstream docs | **Permanently skipped.** No clear scoring semantics — what would a vote on a procedural amendment to a Senate Rules document score against? |

**For treaty + procedural cases, log an info-level skip** with the natural key and reason. If volume is unexpectedly high, that's a signal to investigate (e.g., a wave of treaty amendments could indicate we should consider treaty ingestion).

**Sub-amendment depth bounds:** the recursive CTE caps depth at 10 to prevent infinite-loop bugs from corrupted `parent_amendment_id` cycles. Real Congressional sub-amendment chains rarely exceed 2-3 levels (an amendment to an amendment to a bill is the typical maximum). If we hit the depth bound, log a warning — likely indicates either upstream data quality issue or our placeholder linkage is wrong.

## Vote Weights — authoritative (per Q1 acceptance from previous turn)

| Vote type | Weight | Rationale |
|-----------|-------:|-----------|
| Final passage (bill) | 1.0 | unchanged — definitive position on the legislation as a whole |
| Procedural (bill) | 0.3 | unchanged — procedural votes carry weak policy signal |
| **Amendment vote (substantive — vote on adoption/rejection)** | **0.7** | Amendment votes split caucuses on substantive policy questions and are often the highest-signal data in a member's record. Lower than final passage because amendment scope is narrower than the whole bill |
| **Amendment vote (procedural — motion to table, motion to recommit, cloture on amendment)** | **0.2** | Procedural amendment votes carry even weaker signal than bill procedural votes — typically party-line maneuvering rather than substantive policy expression |

`vote_weight_type` enum extended with `AMENDMENT_SUBSTANTIVE` and `AMENDMENT_PROCEDURAL`. Score-time dispatch table:

| `legislation_type` | `vote_type` | `vote_weight_type` |
|---|---|---|
| HR / S / HJRES / SJRES / etc. (bill types) | Passage | `BILL_PASSAGE` (existing) |
| HR / S / etc. | Procedural | `BILL_PROCEDURAL` (existing) |
| HAMDT / SAMDT / SUAMDT | Passage / "On Adoption" | **`AMENDMENT_SUBSTANTIVE`** |
| HAMDT / SAMDT / SUAMDT | Procedural / Motion to Table / Cloture | **`AMENDMENT_PROCEDURAL`** |

## Legislator Profile Construction Extension (§11.2 changes)

`LegislatorProfileConstructor.construct(memberId, topics)` extended to UNION amendment stances:

```sql
SELECT topic, stance_direction, finding_id, ...
FROM member_bill_stance_topics
WHERE member_id = $memberId AND topic IN ($topics)

UNION ALL

SELECT topic, stance_direction, finding_id, ...
FROM member_amendment_stance_topics  mast
JOIN member_amendment_stances        mas ON mas.id = mast.stance_id
WHERE mas.member_id = $memberId AND mast.topic IN ($topics)
```
