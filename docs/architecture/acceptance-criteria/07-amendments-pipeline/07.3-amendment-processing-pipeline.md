# 7.3 Amendment Processing Pipeline

> Part of [Component 7 — Amendments Pipeline](../07-AMENDMENTS-PIPELINE.md)

## Overview

The core pipeline logic for `amendments-pipeline`. Streams amendments from `AmendmentsApiClient`, detects changes via `ChangeDetector`, creates placeholder members/bills, and upserts to AlloyDB. No events are emitted — bill re-analysis is triggered by new bill text, not by amendment recording.

## Classes

### `AmendmentProcessor[F[_]]`

```
class AmendmentProcessor[F[_]: Async](
  apiClient: AmendmentsApiClient[F],
  amendmentRepository: AmendmentRepository[F],
  placeholderCreator: PlaceholderCreator[F],
  memberRepository: EntityRepository[F, MemberDO],
  billRepository: EntityRepository[F, BillDO],
  config: AmendmentsConfig,
  logger: PipelineLogger[F]
)
```

#### `streamAll(runId: UUID): Stream[F, ProcessingResult]`

Primary pipeline entry point.

1. Compute lookback: `fromDateTime = Instant.now.minus(config.lookbackDays, ChronoUnit.DAYS)`
2. **Iterate per-congress** (per Q8 — mirrors votes-pipeline pattern): for each `congress` in `config.congresses` (the inclusive `Range` from `congressesMin` to `congressesMax`), call `apiClient.fetchAll(FetchParams(congress = Some(congress), fromDateTime = Some(fromDateTime)))`. Concatenate streams. **Pre-102 congresses are rejected at config-load** by `AmendmentsConfig.require` (per Q9 — `MIN_AMENDMENT_CONGRESS = 102`). The API endpoint is `/amendment/{congress}` per congress.
3. **Per page (per P2 batch optimization):** as each list page arrives, batch-prefetch stored amendments before `parEvalMap`. Pseudocode:
   ```scala
   pagedStream
     .chunks                                                   // group items by their natural page boundary
     .evalMap { pageChunk =>
       val keys = pageChunk.toList.map(item => naturalKeyOf(item))
       amendmentRepository.findByNaturalKeys(keys).map { storedMap =>
         pageChunk.toList.map(item => (item, storedMap.get(naturalKeyOf(item))))
       }
     }
     .flatMap(Stream.emits)
     .parEvalMap(config.parallelism) { case (item, storedOpt) =>
       processAmendment(item, storedOpt, ...)
     }
   ```
   This converts N per-amendment SELECTs into 1 SELECT-per-page-IN-clause. For default page size 250, that's 250× fewer round-trips on the change-detection pre-filter.

4. **Per-amendment** (inside `parEvalMap(config.parallelism)`):
   - **Generate a fresh `correlationId = UUID.randomUUID()` per LIST-page amendment.** This correlation id is **threaded through every recursive frame** — sub-amendment recursion does NOT generate a new id; the parent and child share the same correlation context so logs trace cleanly through the chain. Mirrors [VoteProcessor lines 114, 137](../../../../votes-pipeline/src/main/scala/repcheck/ingestion/votes/pipeline/VoteProcessor.scala). The `runId` parameter remains for `WorkflowStateUpdater` and run-level summary aggregation but is **not** the per-item correlation ID.
   - Construct `naturalKey`: `{congress}-{amendmentType}-{number}` from list item fields
   - Call `processAmendment(naturalKey, listItemOpt = Some(item), storedOpt, depth = 0, correlationId)`. Returns `ProcessingResult`.

> **No "stuck amendment" tracking.** Transient errors retry through `RetryWrapper`. Systemic errors (DTO→DO failure, malformed Congress.gov data) log + return `Failed`; the next cron tick retries from scratch. No `failure_count` column, no skip-after-N. Adding that complexity to ingestion buys nothing — the next run either succeeds or re-logs the same systemic failure for the operator to investigate.

> **No cycle guard, only depth bound** (per S1 simplification). Congress.gov can't produce parent cycles by definition (the amendment chain is structurally a tree rooted at a bill). Earlier drafts threaded `Set[String] inFlight` through every recursive frame to defend against impossible data; the cost (one extra parameter through every recursion site) was not worth the protection. The depth bound (`config.maxRecursionDepth`, default 10) is the safety net for runaway recursion regardless of cause — corrupt data, depth-bug regression, or genuine deep chain — without the per-frame `Set` plumbing.

> **Connection-pool sizing (per P1).** Recursion can hold up to `parallelism × maxRecursionDepth` connections concurrently if the chain is fully cold. With defaults (`parallelism=4, maxRecursionDepth=10`), that's 40 concurrent connections during deep-chain hydration. **`AmendmentPipelineApp` MUST set `maximumPoolSize = parallelism × maxRecursionDepth + 5 = 45`** in HikariCP config. The +5 buffer covers the workflow-state writer + bookkeeping queries that run alongside the main pipeline. With the bills-pipeline default of 10, a deep chain at parallelism=4 deadlocks. Document this in `application.conf` with a comment cross-referencing this decision.

#### Change Detection Fields

Two-stage detection:

**Stage 1 — fast pre-filter (no detail call):**

Two checks run in order — placeholder detection first (any required field NULL → hydrate), then `updateDate` comparison.

**1a. Placeholder detection — any required field NULL → `New`, force detail fetch:**

A row counts as a placeholder needing hydration if **any** of these "required fields" — fields that the Congress.gov API guarantees a value for on every real amendment — is NULL on the stored row:

| Required field | Why guaranteed by upstream |
|---|---|
| `congress` | Path component of every amendment URL |
| `amendmentType` | Path component; one of HAMDT/SAMDT/SUAMDT |
| `number` | Path component |
| `chamber` | Always derivable from `amendmentType` (HAMDT→House, SAMDT/SUAMDT→Senate); upstream populates it |
| `updateDate` | Documented as always present in both list and detail responses |

If `stored` has any of those NULL → return `ChangeReport.New`, fetch detail, and run `processAmendment`. This handles three states uniformly:
- placeholder created by votes-pipeline (all NULL except natural-key components)
- partial row from a prior pipeline run that crashed mid-conversion (some columns populated, others NULL)
- pre-existing row written by a future-but-broken extension (any NULL in the required set)

**Why not check optional fields too:** `description`, `purpose`, `sponsorBioguideId`, `billId`, `submittedDate`, `proposedDate`, `latestAction*`, `apiUrl` can all be legitimately NULL in real Congress.gov data — `description` is documented as House-only, sponsors can be empty, `billId` is NULL for standalone amendments, etc. Including them in the placeholder check would force re-hydration on every run for amendments that genuinely have no description/sponsor/etc. — defeats the change-detection short-circuit entirely.

**1b. `updateDate` comparison — only when stage 1a found no placeholder:**

- `listItem.updateDate <= stored.updateDate` → `Unchanged`, skip detail fetch entirely. Steady-state path.
- `listItem.updateDate > stored.updateDate` → `Updated`, proceed to stage 2.
- `listItem.updateDate < stored.updateDate` (data regression) → log warning, return `Skipped` with reason `"regression"`. Indicates the upstream `updateDate` went backwards — typically a Congress.gov data correction we should not let overwrite our newer record.

**Stage 2 — full field-by-field diff (after detail fetch, observability only):**
After `apiClient.fetchDetail` returns `AmendmentDetailDTO`, the converted `AmendmentDO` is diffed field-by-field against the stored row. The diff is **logged at info level for observability** but does not gate persistence — any `Updated` from stage 1 unconditionally writes through. Compared columns:

| Compared (DTO-sourced) | Excluded (RepCheck-internal / pipeline-managed) |
|---|---|
| `congress`, `amendmentType`, `number` | `amendmentId` (surrogate PK) |
| `naturalKey` (derived from above three) | `createdAt` |
| `billId` (surrogate) | `updatedAt` |
| `chamber` | `lastTextCheckAt` (managed by §7.5) |
| `description`, `purpose` | (no `text_versions_count` — dropped per S2) |
| `sponsorMemberId` (surrogate) | |
| `submittedDate` | (no `proposedDate` — Congress.gov API has no such field) |
| `latestActionDate`, `latestActionTime`, `latestActionText` | |
| `updateDate` | |
| `apiUrl` | |

> **Why exclude `createdAt` and `updatedAt`:** these are RepCheck audit columns — `updatedAt` advances on every upsert by design, so including it in the diff would always show a change and the diff log would lose its signal. See §7.2 Date Semantics for the full rationale.

> **`ChangeDetector` pre-filter:** The list endpoint provides `updateDate` for each amendment. `ChangeDetector` uses the fast `updateDate` comparison to skip unchanged amendments without a detail API call. Only amendments with a newer `updateDate` proceed to `fetchDetail`. This follows the same pattern as bills (Component 4 §4.3).

#### `processAmendment(naturalKey: String, listItemOpt: Option[AmendmentListItemDTO], storedOpt: Option[AmendmentDO], depth: Int, correlationId: UUID): F[ProcessingResult]`

The single recursive primitive for ingesting an amendment. Used both by:
- The top-level stream loop (passes `Some(listItem)`, the batch-fetched `storedOpt`, `depth = 0`, and a fresh `correlationId`).
- Itself (when a sub-amendment needs its parent fully resolved before `bill_id (resolved ancestor)` can be set on the child) — recursive call passes `listItemOpt = None`, freshly-fetched `storedOpt`, `depth + 1`, and **the same `correlationId`** (per spec — child + parent share one correlation context so logs trace cleanly through the chain).

The function **drains the entire parent chain to the bill before persisting any row**. By the time `upsert` is called for a child, its parent already has `bill_id (resolved ancestor)` populated. As a result there is no end-of-run sweep — the data is consistent on every commit.

1. **Depth guard (per S1 — only safety net needed):** if `depth > config.maxRecursionDepth` (default 10) → log warning, return `ProcessingResult.Failed(naturalKey, "AmendmentRecursionTooDeep")`. No real legislative chain should exceed 3–4 levels; depth 10 is the practical safety net. **No cycle guard** (per S1) — Congress.gov can't produce parent cycles structurally; the depth bound covers any corrupt-data edge cases regardless.

2. **Idempotency check:** Using `storedOpt` (passed in by the caller — already fetched in the page batch by P2):
   - If `storedOpt.exists(_.updateDate.isDefined)` AND `listItemOpt.exists(item => item.updateDate <= storedOpt.get.updateDate)` → return `ProcessingResult.Skipped(naturalKey, "unchanged")`.
   - If recursive caller (no `listItemOpt`) AND `storedOpt.exists(_.updateDate.isDefined)` AND parent's `bill_id (resolved ancestor)` already populated → return `Succeeded(naturalKey)` immediately; the caller reads the hydrated row without re-fetching.

3. **Fetch detail:** `apiClient.fetchDetail(naturalKeyToUrl(naturalKey))` → `AmendmentDetailDTO`. Single API call per recursion frame; the cost note below covers backfill amplification.

5. **Resolve sponsor placeholder** — reuses the [`PlaceholderCreator` pattern](../../../../bill-metadata-pipeline/src/main/scala/repcheck/ingestion/bills/metadata/pipeline/MemberResolver.scala) bills-metadata-pipeline already uses for the same purpose. **No new method on `MemberRepository`** — `MemberInsertSql` (`ON CONFLICT (natural_key) DO NOTHING`) plus the existing `findByBioguideId` is exactly the right shape.
   ```scala
   detail.sponsors.flatMap(_.headOption).map(_.bioguideId) match {
     case Some(bioguide) =>
       for {
         _        <- placeholderCreator.ensureExists[MemberDO](bioguide, memberRepository)
         memberId <- memberRepo.findByBioguideId(bioguide).map(_.map(_.memberId)).transact(xa)
       } yield memberId  // Option[Long] — surrogate id used as AmendmentDO.sponsorMemberId
     case None =>
       Async[F].pure(Option.empty[Long])
   }
   ```

6. **Resolve bill placeholder** — reuses [`BillRepository.upsertPlaceholder`](../../../../bills-common/src/main/scala/repcheck/ingestion/bills/common/persistence/BillRepository.scala) (existing, `F[Unit]`) followed by `findByBillId`. Same pattern as votes-pipeline's [`BillLookup.forContext`](../../../../votes-pipeline/src/main/scala/repcheck/ingestion/votes/pipeline/BillLookup.scala). **No new method on `BillRepository`.**
   ```scala
   detail.amendedBill match {
     case Some(amended) =>
       val bnk = s"${amended.congress}-${amended.`type`.toUpperCase}-${amended.number}"
       for {
         _      <- billRepo.upsertPlaceholder(bnk).transact(xa)
         billId <- billRepo.findByBillId(bnk).map(_.map(_.billId)).transact(xa)
       } yield billId  // Option[Long]
     case None =>
       Async[F].pure(Option.empty[Long])
   }
   ```

7. **Resolve parent — RECURSIVE** (when `detail.amendedAmendment` is defined — sub-amendment case):
   ```scala
   val parentNk = s"${parent.congress}-${parent.`type`.toUpperCase}-${parent.number}"
   parentExisting ← amendmentRepo.findByNaturalKey(parentNk).transact(xa)

   parentExisting match {
     // Parent already fully hydrated AND has its own bill_id (resolved ancestor) resolved — use as-is.
     case Some(p) if p.updateDate.isDefined =>
       (Some(p.id), p.billId).pure[F]

     // Parent missing OR is a placeholder (updateDate.isEmpty) OR parent has updateDate but
     // bill_id (resolved ancestor) NULL (its own parent wasn't hydrated yet) — recurse to drain the chain.
     case otherwise =>
       processAmendment(
         naturalKey    = parentNk,
         listItemOpt   = None,                   // recursive caller — no list-item context
         storedOpt     = otherwise,              // pass through what we just looked up
         depth         = depth + 1,
         correlationId                           // SAME id — child + parent share log context
       ).flatMap { _ =>
         // After recursion returns, the parent row exists with bill_id (resolved ancestor) populated
         // (or NULL if the chain itself terminates without a bill — treaty / procedural).
         amendmentRepo.findByNaturalKey(parentNk).transact(xa)
       }.map { hydrated =>
         (hydrated.map(_.id), hydrated.flatMap(_.billId))
       }
   }
   ```
   The recursion returns once the **entire** ancestor chain is hydrated. `depth` bounds runaway recursion (per S1 — no cycle set tracking).

   > **Per L2 — known wasted-call under parallel processing (acceptable).** When two amendments A and B with shared parent C are processed in parallel via `parEvalMap`, both can independently fetch C's detail before either commits. `upsertPlaceholder` + `upsert` use `ON CONFLICT` so no duplicate rows result, but C is fetched from Congress.gov twice. Mitigation is not worth the cost of a global "in-flight resolution" lock — the wasted call is bounded by the natural fan-out of an amendment chain (typically <5 children per parent) and the steady-state cost is negligible. Document this in observability so a spike in `congress_gov_detail_fetches_total` during backfill isn't surprising. Per P6 — if the cost ever materially matters, switch to pre-resolution: collect all parent natural keys from the page, batch-resolve before the per-amendment loop starts.

   > **Why we don't `upsertPlaceholder` and stop:** an earlier draft created a placeholder row for the parent and deferred hydration to an end-of-run sweep. That meant `bill_id (resolved ancestor)` was unresolved at the moment the child was persisted, and a separate sweep had to fix it up later. The recursive approach is simpler — by the time we persist the child, its parent already has `bill_id (resolved ancestor)` set, and `computeEffectiveBillId` is a deterministic single-row lookup with no eventually-consistent fixup needed.

   > **Mutual exclusivity in the upstream DTO:** `amendedBill`, `amendedAmendment`, and `amendedTreaty` are not all populated simultaneously — typically exactly one is, occasionally none (procedural amendment). The processor handles each independently: bill resolve fires only when `amendedBill` is populated; parent recursion fires only when `amendedAmendment` is populated. If both are populated (rare upstream data quirk), both are recorded — `bill_id` is the direct reference, parent linkage is preserved for audit, and `bill_id (resolved ancestor)` falls back to `bill_id` (direct beats inherited).
   >
   > **`amendedTreaty` is NOT resolved** — RepCheck doesn't ingest treaties. When DTO has `amendedTreaty` populated and `amendedBill IS NULL` and `amendedAmendment IS NULL`, the row gets `bill_id=NULL, parent_amendment_id=NULL, bill_id (resolved ancestor)=NULL`. Future scoring/analysis treats those as orphans and skips them.

   > **Cost note:** recursive parent resolution can add multiple detail-fetch API calls per discovered sub-amendment chain. In steady state this is rare (parents are typically already hydrated from prior runs and short-circuit at step 3). During initial historical backfill, sub-amendment chains may force several extra detail fetches — bounded by `maxRecursionDepth` and visible in the API budget. Per Q6, this is the correct cost for guaranteed-consistent resolution at ingest time.

8. **Convert DTO to DO with resolved ids:** call `detail.toDO(billId = resolvedBillId, sponsorMemberId = resolvedSponsorMemberId, parentAmendmentId = resolvedParentAmendmentId)` — the new overload added to shared-models 0.1.40 per [P7.0](PRODUCTION_TASKS.md). Returns `Either[String, AmendmentDO]`.
   - `Left(reason)` → log warning, return `ProcessingResult.Failed(naturalKey, reason)`. The next cron tick will retry from scratch; if the upstream data is genuinely malformed, the next run logs the same systemic failure.
   - `Right(amendmentDO)` → continue.

9. **Compute resolved-ancestor `billId` from already-resolved values** (no DB lookup needed — parent's value was just read in step 7):
   ```scala
   val resolvedAncestorBillId: Option[Long] =
     resolvedBillId         // direct case wins (this amendment modifies a bill)
       .orElse(parentBillId)  // inherit from parent's already-resolved ancestor (read in step 7)
   // None means: treaty / procedural / orphan — legitimate, no fixup required
   ```

10. **Upsert (single transaction):** populate the DO with `bill_id` set to the resolved ancestor, then `amendmentRepository.upsert(amendmentDO)`. Returns the persisted DO with surrogate `id`.
    - No history archival (per index file design decision).
    - No child table writes (single DO).
    - Single SQL statement — no multi-table transaction needed.

11. **Log:** `"Amendment {naturalKey} upserted ({N} field changes), bill_id (resolved ancestor)={resolved}"` at info level.

12. Return `ProcessingResult.Succeeded(naturalKey)`.

> **No event emission.** §7.5 (text availability checker) is cron-driven, not event-driven (per Q10 — mirrors `bill-text-availability-checker`). No `amendment.metadata.ingested` topic exists. Downstream consumers discover changes via DB scan.

> **No event emission.** §7.5 (text availability checker) is cron-driven, not event-driven (per Q10 — mirrors `bill-text-availability-checker`). No `amendment.metadata.ingested` topic exists. The amendments-pipeline is a pure data recorder for metadata; downstream consumers discover changes via DB scan.

> **Transaction boundary:** The upsert is a single SQL statement — no multi-table transaction needed (unlike bills which wrap archive + upsert + replace-all in a single transaction).

#### `summarize(results: List[ProcessingResult]): PipelineRunSummary`

Aggregates individual results into a summary:

```
PipelineRunSummary(
  totalProcessed = results.size,
  succeeded = results.count(_.isSucceeded),
  skipped = results.count(_.isSkipped),
  failed = results.count(_.isFailed),
  eventsEmitted = 0,  // amendments-pipeline emits no events; §7.5 discovers via cron
  errors = results.collect { case f: Failed => f.reason }
)
```

### Key Design Decisions

- **Detail fetch for every changed amendment** — the list endpoint lacks sponsor and amended bill data. Every new or updated amendment gets a detail API call.
- **Single amendment failure does not halt the stream** — errors are captured per-amendment as `ProcessingResult.Failed`. The stream continues.
- **Placeholders before upsert** — sponsor and bill placeholder creation happens before amendment upsert so FK constraints are satisfied.
- **Change detection per BEHAVIORAL_SPECS §1** — `updateDate` pre-filter gates the detail fetch; full field-by-field diff is logged for observability but does not gate persistence. See Change Detection Fields above for the exact column set. **Internal audit columns (`createdAt`, `updatedAt`) are explicitly excluded from the diff** so the change report stays driven by Congress.gov truth.
- **Per-amendment correlation ID** — every amendment gets its own `UUID.randomUUID()` generated inside the `parEvalMap` body, threaded into `LogContext` for the entire per-amendment lifecycle (detail fetch, placeholder calls, upsert, error wrapping). Run-level operations (workflow step recording, summary persistence) use the run-scoped `runId` instead. Mirrors votes-pipeline.
- **No events emitted.** This pipeline persists amendment data only. §7.5 discovers fresh amendments via cron-scheduled DB scan, not via events. Bill re-analysis still flows through `bill.text.available` when the amended bill's text is republished — unaffected by amendments-pipeline behavior.
- **No history archival** — amendments rarely change substantively. If needed in the future, add `AmendmentHistoryArchiver` following the same pattern as bills/votes/members.

| **Per-page batch handles missing rows correctly** | Page contains 100 amendments, only 60 in DB → `findByNaturalKeys` returns map with 60 entries; the 40 not-yet-stored amendments are processed as `New` |

| **Recursion: depth guard fires** | Construct fixture with chain depth=11 → recursion at frame 11 returns `Failed("AmendmentRecursionTooDeep")` |
| **Recursion: correlationId propagated through every frame** | Process sub-amendment with depth=3 chain → all log entries (4 frames worth) carry the same `correlationId` |
| **Recursion: parent fully hydrated before child upsert** | Mock fixture: child references parent that is a placeholder (updateDate=NULL); parent's API returns its own amendedBill → child's persisted row has `bill_id (resolved ancestor)` populated transitively |
| **Recursion: parent already hydrated short-circuits** | Pre-populate parent with full data + `bill_id (resolved ancestor)` → child processing skips re-fetch of parent (verifies idempotency check at recursion entry); spy API asserts parent detail NOT fetched |
| **Recursion: sub-amendment with no chain to bill yields bill_id (resolved ancestor) NULL (treaty / procedural)** | Recursion bottoms out at an amendment with no `amendedBill` and no `amendedAmendment` → `bill_id (resolved ancestor) = NULL`; row persists; document as orphan per L8 |
| **Parallel recursion: both children resolve correctly under shared parent** (per L2 — wasted call acceptable) | Spawn 2 fibers for sibling amendments A, B that share parent C. Run concurrently. After completion: exactly 1 row for C, both A and B have correct `parent_amendment_id = C.id` and `bill_id (resolved ancestor)`. Spy API: parent C detail may be fetched 1× or 2× (both acceptable). Spy DB: no FK violations, no duplicate rows. |
| **Parallel recursion: shared parent fetch count counter** | Wire a counter `congress_gov_detail_fetches_total{cause="recursion_redundant"}` and assert it's exposed as a gauge — operator visibility into the L2 wasted-call rate during backfill |
| **Connection pool sizing rejected too-small pool (per P1 negative test)** | At test-time set `maximumPoolSize=5` while running parallelism=4 with depth-3 fixture → recursion deadlocks on connection acquisition within timeout window. Confirms the documented `parallelism × maxRecursionDepth + 5` sizing is required. |
| **Resolved-ancestor `bill_id` computed inline** | Spy repository asserts no `computeEffectiveBillId` / `findByEffectiveBillId` / `updateEffectiveBillId` methods exist on the trait (per 2026-05-05 design — single `bill_id` column carries this semantic). The processor constructs the resolved-ancestor `billId` from in-scope `resolvedBillId.orElse(parentBillId)` and passes it directly to `upsert`. |
