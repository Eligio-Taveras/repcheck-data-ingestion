# 7.7 Docker-Compose Integration + Holistic E2E Tests

> Part of [Component 7 — Amendments Pipeline](../07-AMENDMENTS-PIPELINE.md)
>
> Pulls together the docker-compose service additions, ofelia scheduling, WireMock fixtures, and the cross-pipeline E2E test scenarios. Per-area scenarios live in their own files (§7.4 placeholder tests, §7.6 download tests). This area is the **holistic** spec — proving the new pipelines wire correctly with each other AND with the existing apps.

## Why a dedicated area file

Earlier areas spec the per-component contract (§7.1 API, §7.2 repo, §7.3 metadata pipeline, §7.4 votes integration, §7.5 availability checker, §7.6 text pipeline). What they don't capture is the **cross-pipeline wiring** — the operational concerns that surface only when the full stack runs together against the docker-compose harness:

- Env var names matching application.conf
- Container `depends_on` ordering ensuring init containers complete first
- Pub/Sub topics + subscriptions created and named correctly (avoiding "dead-letter on first publish" bugs)
- WireMock URL patterns covering every path the new pipelines hit
- Schema migration versions matching the columns referenced by new code
- Ofelia cron offsets sequenced to avoid stepping on one another and on existing pipelines
- The new event topics not interfering with existing event consumers

The wiring stage is where most "everything works locally but breaks in the compose stack" bugs live. This area file makes those expectations explicit.

## `pubsub-init.sh` additions

The existing init script creates topics + subscriptions for `bill-text-available`, `member-updated`, `vote-events`. Add **one** pair only:

```sh
# Amendment text availability — emitted by §7.5 (cron), consumed by §7.6
create_topic "amendment-text-available"
create_subscription "amendment-text-available-pipeline-sub" "amendment-text-available"
```

**No `amendment-text-ingested` topic.** §7.6 emits no completion event — downstream consumers (analysis, scoring; both deferred plans) poll `amendment_text_versions WHERE fetched_at IS NOT NULL`. Same pattern as the bill-side post-event-removal model.

**No `amendment-metadata-ingested` topic.** §7.3 emits nothing — downstream consumers discover new amendments via DB scan.

## `ofelia-config.ini` additions

`amendments-pipeline` AND `amendment-text-availability-checker` get cron entries (per Q10 — both are scheduled jobs). Only `amendment-text-pipeline` is event-driven and stays out of Ofelia.

**Both new pipelines run on a common 4-hour cadence** (per directive L10) so the checker is guaranteed to run within the same cycle as a fresh amendments-pipeline pass. Ordered offsets within each 4h tick:

```ini
; amendments-pipeline at minute 30 of every 4h tick.
; Sequenced AFTER bill-metadata + member-profile (which run on the 6h grid)
; so referenced bills/members are likely already present.
[job-run "amendments"]
schedule = 30 */4 * * *
container = amendments-pipeline

; amendment-text-availability-checker at minute 50 — same 4h tick, 20 minutes
; after amendments-pipeline starts, so newly-ingested amendments from the same
; cycle are eligible candidates.
[job-run "amendment-text-checker"]
schedule = 50 */4 * * *
container = amendment-text-availability-checker
```

20-minute offset between amendments-pipeline kickoff and the text checker is generous — even at the 75-percentile cron run length, amendments-pipeline finishes inside the window. If amendments-pipeline runs long on a particular cycle, the checker simply picks up those amendments next cycle (4h later) — self-healing by design.

Updated cron grid (existing + new):

| Minute | Pipeline | Cadence | Notes |
|-------:|---|---|---|
| 0 (every 6h)    | bill-metadata-pipeline | 6h | Existing |
| 30 (every 6h)   | bill-summary-pipeline | 6h | Existing |
| **30 (every 4h)** | **amendments-pipeline** | **4h** | **New** — 4h cadence so text checker can find fresh data within the same cycle |
| **50 (every 4h)** | **amendment-text-availability-checker** | **4h** | **New** — 20 min after amendments-pipeline kickoff |
| 60 (offset +1h) | bill-text-availability-checker | 6h | Existing |
| 60 (offset +2h) | bill-text-pipeline | 6h | Existing |
| 60 (offset +3h) | member-profile-pipeline | 6h | Existing |
| 60 (offset +4h) | lis-mapping-refresher | 6h | Existing |
| 60 (offset +5h) | votes-pipeline | 6h | Existing — runs LAST so member + amendment placeholders from upstream pipelines are present |

## Service additions to `docker-compose.e2e.yml`

E2E stack mirrors local with two changes: WireMock replaces both `api.congress.gov` and senate.gov, and pipelines are one-shot (run-and-exit) rather than long-running.

```yaml
  amendments-pipeline:
    image: repcheck/amendments-pipeline:e2e
    build:
      context: ./amendments-pipeline
      dockerfile: Dockerfile
    depends_on:
      db-migrations:
        condition: service_completed_successfully
      pubsub-init:
        condition: service_completed_successfully
      wiremock:
        condition: service_started
    environment:
      DATABASE_HOST: alloydb
      DATABASE_NAME: repcheck_e2e
      CONGRESS_GOV_API_BASE_URL: "http://wiremock:8080/v3"   # WireMock takes Congress.gov calls
      CONGRESS_GOV_API_KEY: e2e-test-key
      PUBSUB_EMULATOR_HOST: pubsub-emulator:8085
      # … rest mirrors local
    # No restart policy — one-shot for E2E

  amendment-text-availability-checker:
    image: repcheck/amendment-text-availability-checker:e2e
    # similar — depends on wiremock for /amendment/.../text route
    # Subscriber: runs until subscription drains, then can be Ctrl-C'd by the orchestrator

  amendment-text-pipeline:
    image: repcheck/amendment-text-pipeline:e2e
    environment:
      AMENDMENT_TEXT_DOWNLOAD_BASE_URL_OVERRIDE: "http://wiremock:8080"
      # WireMock serves canned amendment HTML/PDF bytes at known paths
      # No real www.congress.gov calls in E2E
```

`AMENDMENT_TEXT_DOWNLOAD_BASE_URL_OVERRIDE` is a test-only env var that the downloader's URL handling consults: if set, replaces the host portion of the format URL with the override. Production has it unset; E2E uses it to redirect through WireMock. Same pattern bill-text-pipeline uses for its govinfo override.

### Sub-amendment fixture helper (per Q12 — option B)

Hand-authoring 3-amendment-chain fixtures per scenario doesn't scale when scenarios cover varying depths and shapes. The E2E test suite gets a small helper that emits the JSON files programmatically:

```scala
// In docker-compose-e2e/src/test/scala/repcheck/e2e/fixtures/AmendmentChainFixtures.scala

object AmendmentChainFixtures {

  /** Materialize an N-deep amendment chain anchored on a bill.
   *  Returns the list of (path, json) tuples; caller writes them to e2e/wiremock/__files/.
   *  
   *  e.g. mkAmendmentChain(rootBillNk = "117-HR-3684", chainLength = 3, congress = 117)
   *  produces:
   *    amendment-detail-117-samdt-100.json   (amendedBill = bill 3684)
   *    amendment-detail-117-samdt-101.json   (amendedAmendment = samdt 100)
   *    amendment-detail-117-samdt-102.json   (amendedAmendment = samdt 101)
   *  AND the corresponding /amendment/117/samdt list pages.
   */
  def mkAmendmentChain(
    rootBillNk: String,
    chainLength: Int,
    congress: Int,
    amendmentType: String = "samdt",      // "samdt" | "hamdt"
    startNumber: Int = 100
  ): List[(String, Json)]

  /** Materialize the corresponding WireMock mappings to wire each fixture path
   *  to its api.congress.gov URL. Returns mapping JSON suitable for
   *  e2e/wiremock/mappings/.
   */
  def mkAmendmentChainMappings(
    rootBillNk: String,
    chainLength: Int,
    congress: Int,
    amendmentType: String = "samdt",
    startNumber: Int = 100
  ): List[(String, Json)]
}
```

The helper:
- Generates valid `AmendmentDetailDTO` JSON for each link in the chain (matching the upstream OpenAPI shape — `amendedAmendment` populated for non-root, `amendedBill` populated only for root)
- Produces the `/amendment/{c}/{type}/{n}` and `/amendment/{c}/{type}` list/detail mappings
- Optionally produces sub-amendment text fixtures by following the same parent-child structure

E2E scenarios that need sub-amendment chains call the helper in `beforeAll`:

```scala
class AmendmentsCrossPipelineSpec extends AnyFlatSpec with ComposeStackFixture {
  override def beforeAll(): Unit = {
    super.beforeAll()
    val (fixtures, mappings) = AmendmentChainFixtures.mkAmendmentChain(
      rootBillNk = "117-HR-3684",
      chainLength = 3,
      congress = 117
    )
    fixtures.foreach { case (path, json) => writeWireMockFixture(path, json) }
    mappings.foreach { case (path, json) => writeWireMockMapping(path, json) }
  }
}
```

This makes Scenario S2 + S3 + the new "sub-amendment recursive resolution" scenario maintainable as we add depth variations during tuning.

WireMock mappings (in `e2e/wiremock/mappings/`) are added in parallel to point the URL patterns at these fixtures.

## Cross-Pipeline E2E Test Scenarios

The existing `dockerComposeE2eSpec` (in `docker-compose-e2e/src/test/scala/repcheck/e2e/`) is extended with a new test class `AmendmentsCrossPipelineSpec extends AnyFlatSpec`. Same `ComposeStackFixture` lifecycle — bring up the stack once, run scenarios in sequence.

### Scenario S1 — Amendments-pipeline → §7.5 → §7.6 chain (happy path)

| Step | Action | Assert |
|------|--------|--------|
| 1 | Trigger `amendments-pipeline` via `docker compose run` | Container exits 0; `amendments` table has 3 rows (SAMDT/HAMDT/SUAMDT from list fixture) |
| 2 | **Spy publisher assertion (no metadata event)** | Zero messages published — `amendments-pipeline` emits no events. Verifies design contract. |
| 3 | Trigger `amendment-text-availability-checker` (next cron tick or `docker compose run`) | After exit: `amendments.last_text_check_at` non-NULL on all three rows; pre-117th SUAMDT was filtered out by SQL pre-filter (no `/text` API call made for it — verified by WireMock request log) |
| 4 | Poll Pub/Sub `amendment-text-available` topic | One message for the SAMDT row only — HAMDT had empty `textVersions[]`, SUAMDT pre-117 filtered |
| 5 | Wait for §7.6 subscriber to drain | `amendment_text_versions` has one row for SAMDT with `fetched_at` non-NULL; `amendment_text_chunks` has rows with 1024-dim embeddings. **No completion event emitted** — readiness is signaled by `fetched_at IS NOT NULL`. Spy publisher assertion: zero messages on any `amendment-*-ingested` topic (those topics do not exist). |

|------|----------|--------|--------|

### Scenario S5 — Failure modes and idempotency

| Sub-scenario | Action | Assert |
|--------------|--------|--------|
| S5a — Re-run amendments-pipeline | Run twice in succession with no fixture changes | Second run emits 0 events (all stage-1 `Unchanged`); `amendments.updated_at` unchanged on second run; no duplicate Pub/Sub messages |
| S5b — Crash mid-§7.6 | Inject a fault between version-row INSERT and chunk INSERTs | Re-deliver the `amendment.text.available` event → §7.6 detects partial state via NULL `fetched_at`, deletes orphan chunks, re-streams cleanly. Same crash semantics as bill-text-pipeline |
| S5c — govinfo 429 from WireMock | Configure WireMock to return 429 with `X-Ratelimit-Remaining: 0` for the first download attempt, then 200 with `X-Ratelimit-Remaining: 35000` for the retry | §7.6 retries per backoff schedule, eventually succeeds. Counter `amendment_text_download_attempts_total{outcome="govinfo_429"}` increments on the first attempt; `success` on the retry. |
| S5e — re-submission of "Submitted" version (per L6) | Pre-populate `amendment_text_versions` with the SAMDT row marked `fetched_at` non-NULL. Publish a fresh `amendment.text.available` event for the same (amendmentId, SUB, HTML) tuple but with a later `publishedDate`. | §7.6 detects the re-submission via `published_date` newer than stored, treats as a content update: clears existing chunks, re-streams, updates `text_length` and `published_date`. New `fetched_at` reflects the re-fetch time. |
| S5f — Pub/Sub redelivery after ACK (at-least-once semantics) | Publish the same event twice in succession (simulates Pub/Sub at-least-once duplicate delivery) | First delivery: full ingestion. Second delivery: `isAlreadyProcessed` (which checks `fetched_at IS NOT NULL`) short-circuits → `Skipped("already-ingested")` returned, ACK message, no duplicate work. Spy embedder asserts 1× call total across both deliveries. |
| S5g — Ollama unreachable at startup | Stop the `ollama` container before §7.6 starts | §7.6 retries connection per backoff; logs Ollama unreachable warnings; pipelines events stay un-ACKed in subscription so they redeliver after Ollama recovers. NACK on persistent failure (Pub/Sub redelivers per backoff schedule). |
| S5h — connection-pool exhaustion (per P1 sizing) | Run §7.3 against a fixture with deeply-recursive amendment chain (depth 8) at `parallelism=4` against a HikariCP pool of size 5 (intentionally undersized) | Pipeline blocks on connection acquisition, eventually times out. Verifies that the documented `pool size = parallelism × maxRecursionDepth + 5 = 45` is required. **Negative test** — confirms the failure mode the sizing guidance prevents. |
| S5d — Pre-117th amendment in fixture | Include a 115th-Congress amendment in the list fixture | §7.5 SQL pre-filter (`congress >= 117`) excludes it from candidates entirely; `amendment-text-available` not published; row's `last_text_check_at` remains NULL because the candidate query never returned the row to be processed (no API call attempted) |

## Per-pipeline E2E specs (separate from cross-pipeline)

In addition to the cross-pipeline scenarios above, each new pipeline gets its own DockerRequired E2E spec under its own subproject's `src/test`:

| Spec | Location | Coverage |
|------|----------|----------|
| `AmendmentsPipelineE2ESpec` | `amendments-pipeline/src/test/scala/.../e2e/` | Single-pipeline run against AlloyDB Omni Docker singleton + WireMock — covers happy path + retry + change detection without bringing up the full compose stack. Tagged `DockerRequired`. |
| `AmendmentTextAvailabilityCheckerE2ESpec` | `amendment-text-availability-checker/src/test/scala/.../e2e/` | Single-subscriber test using the `pubsub-emulator` Docker container — publishes events, asserts on resulting Pub/Sub state |
| `AmendmentTextPipelineE2ESpec` | `amendment-text-pipeline/src/test/scala/.../e2e/` | Subscriber + downloader test, using WireMock for both Pub/Sub event consumption and download URL fetching |

These complement (not replace) the holistic `AmendmentsCrossPipelineSpec` — the per-pipeline specs catch contract violations within a single subproject; the cross-pipeline spec catches wiring violations between subprojects.

6. Implement §7.6 (text pipeline). Add to docker-compose.local.yml. Validate Scenario S1 step 5 and Scenario S5b/S5c.
7. Add WireMock fixtures + mappings; build the cross-pipeline `AmendmentsCrossPipelineSpec`; wire `dockerComposeE2e` SBT dependencies.
8. Run `sbt dockerComposeE2e/test` end-to-end; confirm all scenarios pass.
9. Confirm Scenario S6 — pre-existing test class still passes.

This sequence ensures each layer can be validated before the next is layered on, so a failure surfaces in the smallest possible change.
