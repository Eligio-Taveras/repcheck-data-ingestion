# 7.1 Amendments API Client

> Part of [Component 7 — Amendments Pipeline](../07-AMENDMENTS-PIPELINE.md)

## Overview

Congress.gov API client for amendment list and detail endpoints. Extends `CongressGovPaginatedClient` (Component 3 §3.1) with amendment-specific detail fetching.

## Classes

### `AmendmentsApiClient[F[_]]`

Extends `CongressGovPaginatedClient[F, AmendmentListItemDTO]` to inherit paginated `fetchAll`.

```
class AmendmentsApiClient[F[_]: Async](
  client: Client[F],
  config: AmendmentsConfig,
  retryWrapper: RetryWrapper[F],
  logger: PipelineLogger[F]
) extends CongressGovPaginatedClient[F, AmendmentListItemDTO]
```

#### `fetchPage(params: FetchParams): F[PagedResponse[AmendmentListItemDTO]]`

Inherited pagination — one page of amendments from the list endpoint.

1. Build URL: `{config.baseUrl}/amendment?api_key={config.apiKey}&offset={params.offset}&limit={params.pageSize}`
2. Append optional query parameters:
   - `congress={params.congress}` if present
   - `fromDateTime={params.fromDateTime}` formatted as `yyyy-MM-dd'T'HH:mm:ss'Z'`
   - `toDateTime={params.toDateTime}` formatted as `yyyy-MM-dd'T'HH:mm:ss'Z'`
   - `sort={params.sort}` (maps `UpdateDateAsc` → `"updateDate+asc"`, `UpdateDateDesc` → `"updateDate+desc"`)

> **URL casing rules — verified against [LoC AmendmentEndpoint.md](https://github.com/LibraryOfCongress/api.congress.gov/blob/main/Documentation/AmendmentEndpoint.md):** the list endpoint accepts an UPPERCASE `type` value when filtering (e.g. `?type=SAMDT`). The detail endpoint path uses LOWERCASE type (`/v3/amendment/117/samdt/2137`). Detail URLs returned in the list response's `url` field are already lowercase — use them verbatim, do not re-case. When constructing detail URLs ourselves (we don't, in initial scope — `fetchDetail` only consumes URLs the list endpoint hands us), use lowercase.
3. Execute GET request via `client`
4. Decode JSON response body:
   - `amendments` array → `List[AmendmentListItemDTO]`
   - `pagination.count` → `totalCount`
   - Compute `nextOffset`: if `items.size == params.pageSize` then `Some(params.offset + params.pageSize)` else `None`
5. On HTTP error: wrap in `AmendmentFetchFailed` with endpoint URL and status code

**Congress.gov list response structure:**
```json
{
  "amendments": [
    {
      "congress": 117,
      "description": "An amendment ...",
      "latestAction": { "actionDate": "2021-08-08", "text": "..." },
      "number": "2137",
      "type": "SAMDT",
      "updateDate": "2021-08-08T12:00:00Z",
      "url": "https://api.congress.gov/v3/amendment/117/samdt/2137"
    }
  ],
  "pagination": { "count": 42, "next": "..." }
}
```

#### `fetchDetail(detailUrl: String): F[AmendmentDetailDTO]`

Fetches full amendment details including sponsor and amended bill reference.

> **Not part of the base trait.** `CongressGovPaginatedClient` is parameterized by the list item DTO type. Detail endpoints return a different type (`AmendmentDetailDTO` vs `AmendmentListItemDTO`), so `fetchDetail` is defined on the entity client, not the base trait (per Component 3 §3.1).

1. Append `?api_key={config.apiKey}` to `detailUrl`
2. Execute GET request via `client`, wrapped in `retryWrapper` with `CongressGovErrorClassifier`
3. Decode JSON response body → `AmendmentDetailDTO`
4. On HTTP error: wrap in `AmendmentFetchFailed`
5. On decode error: wrap in `AmendmentFetchFailed` with raw response body snippet

**Congress.gov detail response structure:**
```json
{
  "amendment": {
    "congress": 117,
    "number": "2137",
    "type": "SAMDT",
    "chamber": "Senate",
    "description": "An amendment ...",
    "purpose": "In the nature of a substitute.",
    "updateDate": "2021-08-08T12:00:00Z",
    "submittedDate": "2021-02-02T05:00:00Z",
    "latestAction": { "actionDate": "2021-08-08", "text": "..." },
    "sponsors": [
      { "bioguideId": "S001217", "firstName": "Rick", "lastName": "Scott", ... }
    ],
    "amendedBill": {
      "congress": 117,
      "number": "3684",
      "type": "HR",
      "title": "Infrastructure Investment and Jobs Act",
      "url": "https://api.congress.gov/v3/bill/117/hr/3684"
    },
    "actions": { "count": 3, "url": "..." },
    "textVersions": { "count": 1, "url": "..." }
  }
}
```

### `AmendmentsConfig`

```
final case class AmendmentsConfig(
  apiKey: String,
  baseUrl: String = "https://api.congress.gov/v3",
  pageSize: Int = 250,
  pageDelay: FiniteDuration = 0.millis,
  lookbackDays: Int = 7,
  parallelism: Int = 4,
  // Per S3 simplification — bounded range, not arbitrary List[Int].
  // Min defaults to MIN_AMENDMENT_CONGRESS (102 per Q9). Max defaults to current congress.
  // Operators can shrink the range for partial backfill (e.g. min=119, max=119 for current-only)
  // or widen for a multi-congress historical run.
  congressesMin: Int = 102,
  congressesMax: Int = 119,    // bumped manually each new congress; could be derived
  maxRecursionDepth: Int = 10, // depth bound for §7.3 inline parent recursion (per S1 — cycle guard removed; depth alone is the safety net)
  retry: RetryConfig = RetryConfig(
    maxRetries = 3,
    initialBackoff = 500.millis,
    maxBackoff = 30.seconds,
    timeout = 30.seconds
  ),
  http: HttpClientConfig = HttpClientConfig()
) {
  require(congressesMin >= 102, s"congressesMin must be >= 102 (MIN_AMENDMENT_CONGRESS), got $congressesMin")
  require(congressesMax >= congressesMin, s"congressesMax ($congressesMax) must be >= congressesMin ($congressesMin)")
  def congresses: Range = congressesMin to congressesMax
}
```

> **`lookbackDays`, `parallelism`, `congressesMin`/`Max`, `maxRecursionDepth`** are pipeline-level config used by `AmendmentProcessor` (§7.3) but bundled here for convenience — PureConfig loads the entire config tree from a single HOCON block. The API client itself only uses `apiKey`, `baseUrl`, `pageSize`, `pageDelay`, `retry`, and `http`.

> **Why a Range, not a List** (per S3): bounded range expresses intent ("everything from min to max") and validates more easily. The alternative — `List[Int]` with arbitrary entries — was over-flexible: every consumer needed to validate every value ≥ 102, and operators rarely needed gappy ranges. If a non-contiguous backfill is ever required, run the pipeline twice with different min/max — cheap and explicit.

> **Initial historical backfill** (per Q21 + Q22 — local-first, then DB copy to production):
>
> The backfill runs **locally against a developer machine's database**, not in production. Once the local DB is fully populated, **the operator copies the populated DB into the production environment** (e.g. `pg_dump` from local AlloyDB Omni → `pg_restore` into production AlloyDB). Production amendments-pipeline starts in steady-state-only mode — no historical backfill from production.
>
> **Why local-first** (per Q22):
> - Production never sees the 18-hour backfill API budget hit. Production amendments-pipeline boots with the historical data already there.
> - Failures during backfill are local-only — no half-populated production DB, no need to alert/rollback.
> - Easy to iterate: if the backfill misses something or extraction needs tuning, re-run locally before any production impact.
>
> **Local backfill procedure** (per Q21 — option B, weekend burst with throttling):
>
> 1. Deploy amendments-pipeline locally via docker-compose (`docker-compose.local.yml` per §7.7).
> 2. Pause other Congress.gov-API consumers (bill-metadata-pipeline, member-profile-pipeline, etc.) for the burst window — they share the 5K/hour API key budget.
> 3. Set burst-tuned config (per P7 — different from steady-state):
>    - `AMENDMENTS_PIPELINE_CONGRESSES_MIN=102, _MAX=119`
>    - `AMENDMENTS_PIPELINE_LOOKBACK_DAYS=999999`
>    - **`AMENDMENTS_PIPELINE_PARALLELISM=1`** — backfill prefers tight rate control over throughput; parallelism=1 gives deterministic API pacing
>    - **`AMENDMENTS_PIPELINE_PAGE_DELAY=750ms`** — throttles to ~4800 req/hour, headroom under the 5K/hour limit
> 4. Trigger a one-shot run. Pipeline iterates congresses 102→119 sequentially within the same job. Sub-amendment proactive hydration adds 10-30% per-congress overhead.
> 5. Estimated wall-clock: ~24-30 hours of continuous run. Run over a weekend.
> 6. Resume on interruption: amendments-pipeline change-detection short-circuits already-ingested rows on re-run. No data loss; just re-run with the same config.
> 7. Once complete, run text-availability checker (§7.5) and amendment-text-pipeline (§7.6) locally to populate text — these have their own budget (govinfo CREC, 36K/hour) and are independent.
>
> **Production cutover:**
> 1. Stop local pipelines.
> 2. `pg_dump` local AlloyDB Omni `repcheck` schema. Tables in this plan's scope: `amendments`, `amendment_text_versions`, `amendment_text_chunks`. (Amendment analysis / scoring tables — `amendment_findings`, `amendment_complexity_scores`, etc. — belong to deferred plans and are NOT part of this dump.)
> 3. `pg_restore` into production AlloyDB.
> 4. Production amendments-pipeline boots in **steady-state mode** (`congressesMin = 102, congressesMax = 119`, `lookbackDays = 7`, `parallelism = 4`, `pageDelay = 0ms`). No historical backfill triggered.
> 5. Production §7.5 + §7.6 boot in their normal cron / subscriber modes.
>
> **Steady-state vs backfill config** (per P7):
>
> | Setting | Backfill (one-shot, manual) | Steady-state (production cron) |
> |---|---|---|
> | `parallelism` | **1** (tight rate control) | **4** (throughput) |
> | `pageDelay` | **750ms** (rate-limit headroom) | **0ms** |
> | `lookbackDays` | **999999** (full history) | **7** |
> | `congressesMin` / `congressesMax` | 102 / 119 (or partial) | 102 / 119 |
>
> Polling all 18 congresses on a 4-hour cron tick with a 7-day lookback is cheap because most congresses return zero recent items.

### Error Types

```
final case class AmendmentFetchFailed(
  endpoint: String,
  statusCode: Option[Int],
  detail: String,
  cause: Throwable = null
) extends Exception(s"Amendment fetch failed [$endpoint]: $detail", cause)

final case class AmendmentsApiHttpError(statusCode: Int, body: String)
  extends HttpStatusError(statusCode, body)
```

> **Why `cause` is preserved:** the classifier's cause-chain walk (above) needs the original `EmberException` / `IOException` reachable via `getCause`. Wrapping without preserving the cause defeats EOF-as-Transient detection — the wrapper looks like a generic `Exception` and the classifier falls through to Systemic. Mirrors the `BillSummaryFetchFailed(..., cause)` pattern in [bill-summary-pipeline](../../../../bill-summary-pipeline/src/main/scala/repcheck/ingestion/bills/summary/errors/BillSummaryFetchFailed.scala).

### Error Classification

Uses a new `AmendmentsApiErrorClassifier` extending `HttpStatusErrorClassifier[AmendmentsApiHttpError]` with `transientStatusCodes = Set(429, 500, 502, 503, 504)`. **Mirrors [`BillSummariesApiErrorClassifier`](../../../../bill-summary-pipeline/src/main/scala/repcheck/ingestion/bills/summary/errors/BillSummariesApiErrorClassifier.scala) exactly** — including the cause-chain walk that classifies network-level failures as Transient.

| Failure | Classification | Behavior |
|---------|---------------|----------|
| HTTP 429 | Transient | Retry with backoff |
| HTTP 500, 502, 503, 504 | Transient | Retry with backoff |
| HTTP 401, 403 | Systemic | Halt pipeline |
| HTTP 404 | Systemic | Log warning, skip this amendment (detail endpoint may return 404 for recently withdrawn amendments) |
| `org.http4s.ember.core.EmberException` (e.g. `ReachedEndOfStream` mid-page) | **Transient** | Retry with backoff — server-side socket close mid-response is observed routinely on long pagination runs |
| `java.io.IOException` (incl. `SocketTimeoutException`, `ConnectException`) | **Transient** | Retry with backoff |

**Cause-chain walk:** `AmendmentFetchFailed` wraps the underlying network error, so the classifier walks `getCause` recursively (depth-bounded at 16) to detect the transient network failure beneath the wrapper. This is critical — without the walk, a stream EOF would surface as `AmendmentFetchFailed` (an `Exception` the classifier doesn't match) and halt the pipeline. The depth bound prevents pathological cause cycles from infinite-looping the classifier.

## Acceptance Criteria

| Criterion | Test |
|-----------|------|
| `fetchAll` paginates until `items.size < pageSize` | Mock server returns 3 pages (250, 250, 100); verify all 600 items collected |
| `fetchPage` includes `api_key` on every request | Inspect outgoing requests; every one includes `api_key` query param |
| `fetchPage` appends `fromDateTime`/`toDateTime` in ISO format | Set both params → verify query string contains `yyyy-MM-dd'T'HH:mm:ss'Z'` |
| `fetchPage` appends `congress` filter when present | `congress = Some(117)` → query string contains `congress=117` |
| Rate limiting respects configured `pageDelay` between pages | With 100ms delay, 3 pages take >=200ms |
| `fetchDetail` retrieves full amendment by URL | Mock detail endpoint → verify `AmendmentDetailDTO` decoded with sponsors and amendedBill |
| `fetchDetail` includes `api_key` on detail request | Inspect outgoing request → `api_key` present |
| HTTP 429 triggers retry | Mock 429 → retried → succeeds on attempt 2 |
| HTTP 500/502/503/504 classified as Transient | Verify `AmendmentsApiErrorClassifier.classify` returns `Transient` |
| HTTP 401/403 classified as Systemic | Verify `AmendmentsApiErrorClassifier.classify` returns `Systemic` |
| HTTP 404 on detail logged as warning, amendment skipped | Mock 404 → no exception thrown, warning logged |
| `EmberException` (mid-page socket close) classified as Transient | Drop the connection partway through a paginated response → next page retried → run completes |
| `IOException` (incl. SocketTimeout / ConnectException) classified as Transient | Inject `IOException` into cause chain → classifier returns `Transient` |
| Cause-chain walk reaches network error beneath `AmendmentFetchFailed` wrapper | Verify classifier walks `getCause` past the wrapper to find the underlying `IOException` |
| Timeout applies per-request | Mock slow response exceeding timeout → `TimeoutException` (classified Transient via cause-chain walk) |
| PureConfig loads `AmendmentsConfig` from HOCON | Parse sample HOCON → verify all fields populated |
| Defaults applied when optional keys absent | Parse minimal HOCON (apiKey only) → verify defaults |
| **Pagination boundary: exactly-pageSize-items page** has `Some(nextOffset)` | Mock returns exactly 250 items → `nextOffset = Some(250)` (caller proceeds to next page even though that page may be empty) |
| **Pagination boundary: page with `pageSize - 1` items** has `None` for `nextOffset` | Mock returns 249 items → `nextOffset = None` |
| **Pagination boundary: empty first page** | Mock returns 0 items → `nextOffset = None`, `totalCount = 0` |
| **Pagination boundary: single-item page** | Mock returns 1 item with `pageSize=250` → `nextOffset = None` |
| `lookbackDays = 0` is accepted (degenerate case — no amendments) | Build config with `lookbackDays = 0` → `fromDateTime = NOW()` → API returns empty list, pipeline exits cleanly |
| `lookbackDays = 999999` is accepted (full backfill) | Build config with `lookbackDays = 999999` → `fromDateTime` near epoch → API returns full history |
| `congressesMin < 102` rejected at config load | Build HOCON with `congresses-min = 100` → PureConfig + `require` reject with clear message ("must be >= 102") |
| `congressesMax < congressesMin` rejected at config load | Build HOCON with `congresses-min = 119, congresses-max = 110` → rejected ("must be >= congressesMin") |
| `congresses` returns inclusive Range | `AmendmentsConfig(congressesMin = 117, congressesMax = 119).congresses.toList == List(117, 118, 119)` |
