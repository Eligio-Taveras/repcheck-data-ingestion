# 7.4 Cross-Pipeline Integration: Amendment Placeholder Creation

> Part of [Component 7 — Amendments Pipeline](../07-AMENDMENTS-PIPELINE.md)

## Overview

The amendments pipeline is the **owner** of the `amendments` table — it produces the canonical, fully-hydrated rows. But it is not the only writer. Other pipelines that encounter amendment references during their own ingestion must create **placeholder** rows so that vote / cross-entity linkage rows can be persisted with referential integrity (or with stable natural-key references) before the amendments pipeline has had a chance to run.

This area file specifies the cross-pipeline integration:

| Pipeline | Action | Why | Status |
|----------|--------|-----|--------|
| `votes-pipeline` | Creates amendment placeholders via `AmendmentRepository.upsertPlaceholder` | Roll calls reference S.Amdt./H.Amdt. on either chamber. Today these references are silently dropped (see "Current Gap" below). | **In scope — implement** |
| `bill-summary-pipeline` | None | The `/summaries` endpoint returns `actionDate, actionDesc, bill, currentChamber, currentChamberCode, lastSummaryUpdateDate, text, updateDate, versionCode` — the only foreign reference is `bill`. No amendment data flows through summary processing. | **Not applicable — confirmed via OpenAPI spec** |
| `bill-metadata-pipeline` | None | Bill metadata references the bill itself, not its amendments. The `/bill/{congress}/{type}/{number}/amendments` sub-endpoint exists but is not consumed by metadata processing. | Not applicable |
| `bill-text-pipeline` / `bill-text-availability-checker` | None | Text ingestion operates on bill text; amendment text would route through the same path only if/when amendment text is consumed (not in initial scope per §7.1). | Not applicable |
| `member-profile-pipeline`, `lis-mapping-refresher` | None | Member-side ingestion has no amendment surface. | Not applicable |

> **Why this matters:** without placeholder creation, vote rows that reference amendment legislation either drop the linkage entirely (current Senate behavior) or attempt to insert a placeholder bill row keyed to an amendment natural key (current House behavior — would FK-violate against `bills` once an FK is added, or create a polluting bill row today).

## Data Sources

Two distinct concerns, three distinct sources:

| Concern | Source | Format | Domain |
|---------|--------|--------|--------|
| **Amendment metadata** (one row per amendment in the `amendments` table — sponsor, purpose, billId, dates, etc.) — **both chambers** | `GET /v3/amendment[/{congress}[/{type}[/{number}]]]` | JSON | `api.congress.gov` |
| **House amendment-vote linkage** (which amendment a House roll call is on) | `GET /v3/house-vote/{congress}/{session}/{rollCall}` and `…/members` sub-endpoint — `legislationType` field carries `HAMDT`/`SAMDT` directly on amendment votes | JSON | `api.congress.gov` |
| **Senate amendment-vote linkage** | `https://www.senate.gov/legislative/LIS/roll_call_votes/vote{C}{S}/vote_{C}_{S}_{NNNNN}.xml` — `<document_type>` carries `"S.Amdt."` / `"H.Amdt."` / `"S.U.Amdt."` and `<document_number>` carries the amendment number | XML | **`senate.gov` (different domain from everything else)** |

### Source-level differences worth knowing

1. **Format/casing mismatch — Senate XML vs API enum.** Senate XML emits period-punctuated short forms (`"S.Amdt."`, `"H.Amdt."`, `"S.U.Amdt."`) — the API and our enum use compact uppercase (`SAMDT`, `HAMDT`, `SUAMDT`). The Senate converter must map between them, mirroring the existing bill mapping at [SenateVoteConverter.scala:241-253](../../../../votes-pipeline/src/main/scala/repcheck/ingestion/votes/pipeline/SenateVoteConverter.scala). The new cases:
   ```
   case "S.Amdt."     => Right(LegislationRef.Amendment(AmendmentType.SAMDT))
   case "H.Amdt."     => Right(LegislationRef.Amendment(AmendmentType.HAMDT))
   case "S.U.Amdt."   => Right(LegislationRef.Amendment(AmendmentType.SUAMDT))
   ```

2. **Senate XML uses DIFFERENT XML elements for amendment votes** (verified 2026-05-03 against vote `117/1/312` which is on S.Amdt. 2137). For amendment votes, the relevant fields are NOT under `<document>` like bill votes — they're top-level on the `<roll_call_vote>` element:
   ```xml
   <document_type>S.Amdt.</document_type>            <!-- under <document> — populated -->
   <document_number/>                                <!-- under <document> — EMPTY for amendment votes -->
   <amendment_number>S.Amdt. 2137</amendment_number> <!-- top-level — the actual amendment number with type prefix -->
   <amendment_to_document_number>H.R. 3684</amendment_to_document_number>  <!-- top-level — the bill being amended -->
   <amendment_to_document_short_title>INVEST in America Act</amendment_to_document_short_title>
   ```
   The `<amendment_number>` text needs **parsing**: split on whitespace to extract the numeric tail (e.g. `"S.Amdt. 2137"` → `"2137"`). Use the regex below — accepts both ASCII and Unicode whitespace including the non-breaking space (` `) which the Senate XML occasionally uses.

   ```scala
   // Per L5 — verified live against senate.gov vote 117/1/312 on 2026-05-03.
   // The (?U) flag makes \s match Unicode whitespace (incl. NBSP  ) — Java regex
   // by default only matches ASCII whitespace under \s, so NBSP-laden documents would
   // silently fail to parse without (?U).
   private val AmendmentNumberPattern: Regex =
     """(?U)^(?:S\.U\.Amdt\.|S\.Amdt\.|H\.Amdt\.)\s+(\d+)$""".r
   ```

   **`SenateVoteXmlDecoder` and `SenateVoteDocumentDTO` need extending** (votes-pipeline change in scope of §7.4):
   - New top-level fields on the decoded DTO: `amendmentNumber: Option[String]` (raw, with prefix), `amendmentToDocumentNumber: Option[String]`, `amendmentToDocumentShortTitle: Option[String]`.
   - `SenateVoteConverter.classifyDocument` checks `documentType` is amendment-typed; if so, uses `amendmentNumber` (parsed) for `legislation_number` and constructs the parent-bill natural key from `amendmentToDocumentNumber` (parsing `"H.R. 3684"` → `"117-HR-3684"`). The `documentNumber` field, being empty for amendment votes, is ignored.
   - When `<amendment_number>` itself is empty (very old XML / data-quality issue), fall back to skipping placeholder creation but still persisting the vote — mirrors the empty-documentCongress fallback at [SenateVoteConverter.scala:139-149](../../../../votes-pipeline/src/main/scala/repcheck/ingestion/votes/pipeline/SenateVoteConverter.scala).

3. **Older Senate vote XML (109th-Congress era and earlier) routinely emits empty `<document_congress/>`** — see [SenateVoteXmlDecoder.scala:232-242](../../../../votes-pipeline/src/main/scala/repcheck/ingestion/votes/xml/SenateVoteXmlDecoder.scala). For pre-102 amendment votes (out of scope per Q9 of planning) we'd hit this; for in-scope (102+) amendment votes the empty-congress case is rare but the fallback exists.

3. **Two upstream rate budgets.** senate.gov runs hot at low rates: `permits=1, requestDelay=3s` per [SenateVoteXmlConfig.scala](../../../../votes-pipeline/src/main/scala/repcheck/ingestion/votes/config/SenateVoteXmlConfig.scala) — far tighter than Congress.gov's documented `5K/hr` shared across api endpoints. House amendment-vote ingestion shares Congress.gov budget with amendments-pipeline itself plus everything else under `api.congress.gov`. Senate amendment-vote ingestion is the throughput-limited path during backfill. **No new rate-limiter is needed** — the existing senate.gov client config handles it. Backfill plans should expect Senate to dominate elapsed time.

4. **No senate.gov amendment-metadata feed exists.** Even though senate.gov XML is the source for Senate *vote* data, it does **not** carry amendment metadata (description, sponsor, purpose, amendedBill). If senate.gov XML names `S.Amdt. 3937`, the actual row in `amendments` is hydrated only by amendments-pipeline calling `api.congress.gov/v3/amendment/{congress}/samdt/3937`. Congress.gov is authoritative for amendment metadata for both chambers — no chamber-specific metadata source.

## Schema Prerequisites

The following migration must be added to `repcheck-db-migrations` and a new artifact version published before this work can land:

```sql
-- Vxxx__add_amendment_legislation_types.sql
ALTER TYPE legislation_type_enum ADD VALUE IF NOT EXISTS 'HAMDT';
ALTER TYPE legislation_type_enum ADD VALUE IF NOT EXISTS 'SAMDT';
ALTER TYPE legislation_type_enum ADD VALUE IF NOT EXISTS 'SUAMDT';
```

`ALTER TYPE … ADD VALUE` is non-transactional in Postgres; it must run outside a migration block or in a dedicated transaction. The migration framework (`db-migrations-runner`) handles this — see existing enum-extension migrations in the artifact for precedent.

Bump `repcheck-db-migrations-runner` in `build.sbt` once the migration is published.

## Senate Path Changes

### `SenateVoteConverter.normalizeDocumentType`

Extend to recognize amendment document types:

```
case "S.Amdt." => Right(LegislationRef.Amendment(AmendmentType.SAMDT))
case "H.Amdt." => Right(LegislationRef.Amendment(AmendmentType.HAMDT))
// "S.U.Amdt." case INTENTIONALLY omitted: SUAMDT only existed in the 97th-98th Congresses
// (1981-1985), well before the 102nd-Congress cutoff (per Q9 of planning, MIN_AMENDMENT_CONGRESS=102).
// We will never see "S.U.Amdt." in modern Senate vote XML.
```

`LegislationRef` is the new sealed type added to shared-models 0.1.40 (per [P7.0](PRODUCTION_TASKS.md)) with `Bill(BillType)` and `Amendment(AmendmentType)` variants. Generalizes the return type of `normalizeDocumentType` from `Either[NonBillOrUnknown, BillType]` to `Either[NonBillOrUnknown, LegislationRef]`.

### `SenateVoteConverter.classifyDocument`

A `LegislationRef.Amendment` outcome populates the same `legislation_*` columns the bill case populates today:

| Column | Value |
|--------|-------|
| `bill_id` | `None` — amendments do not FK to `bills` |
| `legislation_type` | `Some(SAMDT)` / `Some(HAMDT)` / `Some(SUAMDT)` (from extended enum) |
| `legislation_number` | `Some(documentNumber)` |
| `legislation_url` | `None` for Senate (XML doesn't carry one); use upstream-provided value for House (the Congress.gov votes API returns `legislationUrl` directly in the JSON response — pass it through verbatim, do not synthesize) |

> **Why not synthesize a `www.congress.gov` amendment URL:** unlike bills (where the slug pattern `house-bill` / `senate-bill` is verified live in [SenateVoteConverter.scala:281-291](../../../../votes-pipeline/src/main/scala/repcheck/ingestion/votes/pipeline/SenateVoteConverter.scala) against the API's own returned `legislationUrl`), the Library of Congress upstream documentation does not publish a www.congress.gov permalink slug for amendments — the only documented URL is the API self-link `https://api.congress.gov/v3/amendment/{congress}/{lowercase-type}/{number}`. Inventing `senate-amendment` / `house-amendment` slugs by analogy with bills would be a guess. Defer until either (a) the Congress.gov votes API's `legislationUrl` field for amendment-typed rows reveals the slug live, or (b) the LoC docs add it. Stage-1a (§7.3) does not depend on `legislation_url` for placeholder detection, so leaving it NULL has no functional cost.

The `billNaturalKey` field on `DocumentClassification` becomes `amendmentNaturalKey: Option[String]` (or both fields coexist, populated alternately) so the processor can route to `AmendmentLookup` instead of `BillLookup`.

### Backwards compatibility

Existing votes already in the table with `legislation_type IS NULL` from prior amendment-vote ingestions stay as-is — no backfill of historical Senate votes is required for this work, but a one-shot historical re-run with the wider lookback (using the existing `congressSessions` config) will hydrate them once the converter changes ship.

## House Path Changes

### Routing in `VoteProcessor.processHouseVote`

Currently the House path calls `dto.toDO(billLookup)` from shared-models. With amendments, the lookup must dispatch on `legislationType`:

```
val lookup: String => F[Option[Long]] = nk => dto.legislationType match {
  case Some(t) if isAmendmentType(t) => amendmentLookup.forContext(logCtx)(nk).as(None)
  case _                              => billLookup.forContext(logCtx)(nk)
}
dto.toDO(lookup)
```

`amendmentLookup` returns `F[Unit]` (placeholder created or no-op), wrapped in `.as(None)` because `VoteMembersDTOOps.toDO` expects `Option[Long]` for the surrogate `bill_id` — and amendments deliberately return `None` since votes don't FK to amendments. The `legislation_*` columns on the resulting `VoteDO` are populated from the DTO directly by the existing conversion path; only the side-effect (placeholder creation) is new.

`isAmendmentType(t: String): Boolean` lives in shared-models alongside `AmendmentType` parsing — set membership against `{"HAMDT", "SAMDT", "SUAMDT"}`.

## Repository Access from Votes-Pipeline

**Decision: votes-pipeline calls `AmendmentRepository.upsertPlaceholder(nk).transact(xa)` directly.** No `AmendmentLookup` wrapper class.

> **Why no wrapper** (revised from earlier draft): `BillLookup` exists because it does *real composition* — it bundles `upsertPlaceholder` + `findByBillId` + raise-on-missing into one round-trip (vote rows FK to `bills.id`, so the surrogate id must be resolved). For amendments there is no FK lookup (vote rows reference amendments by natural key only — see Open Question 2 below), so a wrapper would carry only a `LogContext`-bound `handleErrorWith`. That's three lines of boilerplate per call site, not a meaningful abstraction. The processor and converter call the repo directly and inline the error logging where they already have the `LogContext`.

> **What this looks like at the call site:**
> ```
> if (amendmentCongress < Constants.MinAmendmentCongress) {
>   // Pre-102 amendment per Q9 — skip placeholder creation entirely.
>   // Vote row still persists (votes are scoped to their own congress, not amendments-pipeline).
>   meterRegistry.counter("amendment_placeholder_skipped_total", "reason", "pre_102_amendment").inc()
>   logger.info(logCtx, s"Skipping pre-102 amendment placeholder for $naturalKey").as(())
> } else {
>   amendmentRepo.upsertPlaceholder(naturalKey).transact(xa).handleErrorWith { err =>
>     logger.error(logCtx, s"Amendment placeholder failed for $naturalKey", Some(err)) *>
>       Async[F].raiseError[Long](err)
>   }.void  // discard the surrogate id — votes-pipeline doesn't FK to amendments today
> }
> ```
> The vote row itself persists with `legislation_type` and `legislation_number` populated regardless of congress — only the amendment placeholder side is gated. A pre-102 vote on `S.Amdt. 1234` is recorded as a vote, just without a corresponding amendments-table row.
> The repo method returns `F[Long]` (the surrogate id) per §7.2, but votes-pipeline calls `.void` since there's no FK column on `votes` for amendments (per §7.4 Open Question 2 — natural-key-only linkage). Lives in `VoteProcessor` (House dispatch path) and `SenateVoteConverter.classifyDocument` (Senate amendment-classified path). If a third call site emerges later, extract a private helper.

## How votes-pipeline accesses `AmendmentRepository`

**Decision: votes-pipeline depends directly on `amendments-pipeline` for the repository trait + Doobie impl. No new `amendments-common` SBT module.**

> **Rationale:** the alternative — extracting a fresh `amendments-common` module mirroring `bills-common`/`members-common` — was the conservative pick for symmetry with existing convention. Reconsidered:
>
> - `bills-common` and `members-common` exist because **multiple pipelines** read/write those tables: `bills-common` is consumed by `bill-metadata-pipeline`, `bill-summary-pipeline`, `bill-text-availability-checker`, `bill-text-pipeline`, `votes-pipeline`. Five consumers justify a shared module.
> - For amendments, the consumer count is **two** (amendments-pipeline + votes-pipeline). The summary, metadata, text, and members pipelines do not touch `amendments`. Extracting a module for a 2-consumer table is over-engineering.
> - Pulling in `amendments-pipeline` from votes-pipeline costs a few extra classes on the votes-pipeline classpath (`AmendmentsApiClient`, `AmendmentProcessor`, `AmendmentPipelineApp`, error types). None instantiate at runtime — they're just bytecode the JVM never loads. The `assembly` jar gets ~maybe ~10–20KB heavier; in a 100MB+ fat jar that's noise.
> - If a third consumer ever materializes, extract `amendments-common` then. Until then YAGNI.
>
> **Build.sbt change:**
> ```
> lazy val votesPipeline = (project in file("votes-pipeline"))
>   .dependsOn(membersCommon % "compile->compile;test->test")
>   .dependsOn(billsCommon   % "compile->compile;test->test")
>   .dependsOn(amendmentsPipeline)   // NEW — for AmendmentRepository trait + DoobieAmendmentRepository
> ```
>
> Note `amendmentsPipeline` is added with no test-config carry-over — votes-pipeline tests don't need amendments-pipeline test fixtures, just the production trait + Doobie impl.

> **Risk to monitor:** circular-dependency danger if `amendments-pipeline` ever needs to depend back on `votes-pipeline`. Today nothing in §7.1–§7.3 references votes data, and the design intent (amendments emit no events; bill re-analysis flows through bill text) keeps it that way. If a future scope creep introduces a dependency loop, fall back to extracting `amendments-common`.

## Summary-Pipeline: Confirmed Not Applicable

Verified against three sources (1 local snapshot + 2 upstream live docs):

### Source 1 — local OpenAPI spec ([docs/reference/congress-gov-api.yaml](../../../reference/congress-gov-api.yaml))

The `/summaries` response is `{ summaries: [summariesArray], pagination: {…} }`. Each `summariesArray` item contains:

```
actionDate, actionDesc, bill, currentChamber, currentChamberCode,
lastSummaryUpdateDate, text, updateDate, versionCode
```

The `bill` field references the `summaryBill` schema, whose fields are:

```
congress, number, originChamber, originChamberCode, title, type,
updateDateIncludingText, url
```

No amendment fields anywhere.

### Source 2 — Library of Congress upstream API docs (`SummariesEndpoint.md`)

Live-fetched from [github.com/LibraryOfCongress/api.congress.gov](https://github.com/LibraryOfCongress/api.congress.gov/blob/main/Documentation/SummariesEndpoint.md). Confirmed identical field set. Quoting the docs: "The endpoint tracks bill actions and statuses, not amendment details." No `amendments`, `amendedBy`, `amendmentNumber`, or any amendment-shaped field in either the top-level summary item or the nested `bill` sub-object.

### Source 3 — Library of Congress upstream API docs (`BillEndpoint.md`)

The per-bill summaries endpoint `/bill/{congress}/{billType}/{billNumber}/summaries` returns `versionCode, actionDate, actionDesc, updateDate, text` only — no `bill` sub-object (context is already a bill) and no amendment reference. The docs explicitly note amendments are accessed through the separate `/amendment` endpoints.

### Conclusion

**No work is required in `bill-summary-pipeline`.** This row is in the table at the top of this file for completeness — to make the negative result auditable rather than implicit. If Congress.gov ever adds amendment references to the summaries response in a future API version, this section is the canary: the negative result was verified against `summariesArray` and `summaryBill` schemas as of 2026-05-03 and should be re-checked when bumping the local `congress-gov-api.yaml` snapshot.

If amendment text becomes a future deliverable, it would route through `bill-text-pipeline` (via the `/amendment/{...}/text` endpoint enumerated in §7.1's "Minimal initial scope" table — currently out of scope), not through summaries.

## Open Questions

1. **Should an FK constraint exist from `votes` to `amendments`?** Today the votes table has no `amendment_id` column — only `legislation_type` / `legislation_number` strings. Adding a structured FK would require:
   - A new `amendment_id` BIGINT column on `votes`
   - Backfill of existing rows (none today since amendment votes lose their linkage entirely)
   - The lookup pattern would become a true FK lookup (returns `Some(id)`, mirroring `BillLookup`) rather than a side-effect placeholder
   - The decision-not-to-wrap (above) would flip — at that point, an `AmendmentLookup` class would do real composition (upsert + find + raise) and would be worth extracting

   **Decision deferred** — initial scope keeps the natural-key-only linkage to minimize migration churn. FK can be added later; the wrapper-class decision is reversible at that point.
